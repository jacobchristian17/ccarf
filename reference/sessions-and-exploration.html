Decomposition, sessions & long exploration

A one-page cheat sheet, taught in Lesson 6.

Decomposition (1.6)

Task shapePattern
Predictable, multi-aspect (same checks every time)Fixed sequential pipeline (prompt chaining)
Large code reviewPer-file local passes → one cross-file integration pass that receives findings, not the source
Open-ended investigation ("add tests to a legacy codebase")Dynamic: map the structure → high-impact areas → prioritised plan that adapts as dependencies turn up

One pass over many files leads to attention dilution: uneven depth, missed obvious bugs, contradictory verdicts. Subagents all succeed but coverage is wrong → check the decomposition (sample Q7).

Sessions (1.7)

SituationMove
Prior context mostly validResume the named session
…a few files changedResume + name the changed files for a targeted re-read (not a full re-exploration)
Most prior tool results are staleNew session + injected structured summary (stale findings flagged)
Compare divergent approaches from one baselinefork_session once per branch. The original stays unchanged
CLI   claude -n refund-analysis            name it        (/rename mid-session)
      claude -r refund-analysis "…"        resume by name or id      claude -c   most recent
      claude -r refund-analysis --fork-session "…"                   fork on resume
SDK   query({ prompt, options: { title: "refund-analysis" } })      session_id on init + result messages
      options: { resume: id }   ·   { resume: id, forkSession: true }   ·   forkSession(id)   (Py: fork_session=True)
Interactive   /resume · /branch (switch into a copy) · /fork (background copy) · /compact [focus] · /clear

A fork copies the conversation, not the filesystem: edits in one branch are visible to the others. Resume with no change notice → the model trusts stale tool results (lab: 0 re-reads, a confidently wrong answer).

Long exploration (5.4)

  • Symptom: inconsistent answers, "typical patterns" instead of the specific classes found earlier (context degradation / context rot).
  • Scratchpad file: record key findings with file:line, and consult it for later questions. Curate it, because append-only notes bloat (lab: 92 lines in one run).
  • Subagents for verbose discovery ("find all test files", "trace refund flow dependencies"). The main agent keeps the high-level view.
  • Phase summaries: summarise phase N, then inject the summary into phase N+1's initial context.
  • Manifest: each agent exports structured state to a known location, and the coordinator loads the manifest on resume and injects it into the prompts. This gives you handoff and crash recovery from one mechanism.
  • /compact when context fills with discovery output.
state/<agent>.json  { agent, phase, status: done|in_progress|failed, summary, findings[{fact,file,line}], filesRead, openQuestions, updatedAt }
state/manifest.json { runId, updatedAt, agents: { <agent>: { status, stateFile } } }     write .tmp → rename (atomic)
resume: skip done · inject done summaries + findings · mark in_progress findings "interrupted, unverified"

Distractors: bigger context window; repeat the instructions; restart from scratch; resume anyway and correct as you go; fork to "preserve" stale analysis; /compact a stale session; retry until it succeeds; one agent explores both approaches in sequence; re-read every file "to be safe".

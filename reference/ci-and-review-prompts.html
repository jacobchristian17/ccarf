Claude Code in CI & review prompts

A one-page cheat sheet, taught in Lesson 9. A CI review needs to run unattended, return output a machine can post, apply criteria a developer trusts, and come from a reviewer that didn't write the code.

Running in CI (3.6)

claude -p --output-format json \
  --json-schema "$(cat review/finding.schema.json)" \
  --allowedTools "Read,Grep,Glob" --max-turns 20 < prompt.txt > review.json
jq '.structured_output.findings' review.json
NeedUse
Job hangs waiting for input-p / --print: run, print, exit. (Not CLAUDE_HEADLESS, --batch or < /dev/null: those don't exist or don't work)
Parseable output--output-format json: one result envelope. The fields are result, session_id, is_error, subtype, num_turns and total_cost_usd
Output matching a schema, to post as inline commentsAdd --json-schema. The validated object is in structured_output. Check is_error / subtype === "success" first
Project context (review criteria, testing standards, fixtures)CLAUDE.md, which CI-invoked Claude Code reads like any session
Tools in an unattended run--allowedTools pre-approves tools. In -p, anything that would need approval is denied, and the run doesn't hang. A reviewer only needs Read/Grep/Glob
A second step on the same sessionCapture session_id, then --resume <id>. Don't do this to review generated code (see 4.6)

Today: the docs recommend --bare for CI. It skips CLAUDE.md, hooks, skills and MCP discovery, and needs ANTHROPIC_API_KEY. In bare mode, pass context with --append-system-prompt-file. GitHub: anthropics/claude-code-action@v1 with prompt + claude_args.

Re-runs, tests

SymptomFix
Every push re-posts the same commentsPut the prior findings in the prompt, and report only new or still-unaddressed issues (fixed ones disappear). Mark them status: new | still_open, and only new becomes a new comment
Generated tests duplicate existing onesPut the existing test file in context
Generated tests are low-value or ignore fixturesDocument testing standards, valuable-test criteria and the fixtures in CLAUDE.md

Explicit criteria (4.1)

Vague (fails)Explicit (works)
"Check that comments are accurate""Flag a comment only when its claimed behaviour contradicts what the code does"
"Be conservative" / "only high-confidence findings"Categories to report (bugs, security) and to skip (style, documented local patterns). Confidence goes in a field, not into a filter
"Rate severity appropriately"Each level defined with a concrete code example

False positives cost trust across all categories, the accurate ones included. If one category is noisy, disable that category temporarily while you fix its prompt, rather than tuning the whole review "down".

Few-shot examples (4.2)

  • The most effective fix when detailed instructions still give inconsistent output (format, severity, judgement).
  • 2–4 targeted examples (exam). The docs say 3–5, wrapped in <example> tags. Make them relevant and diverse.
  • Aim them at ambiguous cases, and show the reasoning for choosing this action over the plausible alternative.
  • Include an acceptable pattern → no finding example. It cuts false positives and still generalises.
  • Show the exact output format: location, issue, severity, suggested fix.
  • For extraction: examples of varied document formats fix empty or null required fields and reduce hallucination.

Multi-instance & multi-pass review (4.6)

ProblemArchitecture
Generator reviewing its own code in the same sessionA second, independent instance without the generator's reasoning context. "Review carefully" instructions and extended thinking don't remove the anchoring
Large multi-file PR: uneven depth, misses, contradictionsPer-file local passes + a separate cross-file integration pass (data flow, changed contracts). Not a bigger model, not consensus voting
Deciding which findings a human checksA verification pass that self-reports confidence per finding, used to route (calibrate it against labelled samples first)

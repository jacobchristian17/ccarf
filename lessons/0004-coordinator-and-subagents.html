Coordinator and subagents

A subagent knows only what you write in its prompt. Everything in this lesson follows from that.

1 · Hub and spoke: the coordinator owns the plan

In the exam's research system, a coordinator breaks the topic down, delegates to specialist subagents, collects their results and decides what happens next. All communication between subagents goes through the coordinator, which gives you observability, consistent error handling and controlled information flow. Subagents never talk to each other directly.Exam guide, task statement 1.2 (md/CCAR-F/sections/07).

Because everything flows through it, the coordinator is also where most root causes live. In sample Q7, every subagent did its job correctly, yet the report on "AI in creative industries" covered only visual arts. The coordinator's logs showed why: it had split the topic into digital art, graphic design and photography. The decomposition was too narrow. Fixing a downstream agent would not help, because each one handled exactly what it was given.Sample question 7, md/CCAR-F/sections/14.

Coordinator job (1.2)What "good" looks like
DecomposeCovers the full breadth of the topic. Gives each subagent distinct subtopics or source types, so their work doesn't overlap
SelectMatches effort to the query. A single fact needs one searcher, not the whole pipeline
DelegateWrites complete prompts and spawns independent work in parallel
RefineChecks the synthesis for gaps, re-delegates targeted queries, and runs synthesis again

Anthropic's own research system gives the scale: "Simple fact-finding requires just 1 agent with 3-10 tool calls … complex research might use more than 10 subagents." Their early failure mode was vague delegation that made subagents duplicate each other's work.How we built our multi-agent research system, Anthropic Engineering. See "Scale effort to query complexity" and "Teach the orchestrator how to delegate".

2 · Subagents start empty (1.3)

A subagent gets its own system prompt (AgentDefinition.prompt) and the prompt string from the Agent tool call. That's it. It doesn't see the parent's conversation, the parent's tool results, or the parent's system prompt.Subagents in the SDK → What subagents inherit, Claude Code Docs. Two consequences show up on the exam:

  • Repeat the user's constraints in every subagent prompt. If the user said "2026 sources only" and the coordinator doesn't pass it on, the searcher can't know.
  • Give the synthesizer the complete findings, in structure. Keep content apart from metadata: { claim, evidence, source: { id, publisher, published, page } }. If the coordinator hands over a prose summary, the sources are gone and can't be recovered (provenance, the topic of Lesson 5).
Exam heuristic If a subagent "ignores" a constraint or "loses" citations, the cause is almost always what the coordinator put in the prompt. Distractors blame the subagent's model, add shared memory, or ask the subagent to fetch the parent's history. None of those exist. The fix is an explicit, complete, structured prompt.

3 · Spawning: the Agent tool and AgentDefinition

query({ prompt, options: {
  tools: ["Agent"],                               // the coordinator can spawn (exam: "Task")
  allowedTools: ["Agent", "mcp__research__*"],    // auto-approve
  agents: {
    searcher: { description: "Web researcher for ONE assigned subtopic…",   // when to use it
                prompt: "You research one subtopic… return JSON findings",  // its system prompt
                tools: ["mcp__research__web_search"],                       // its ONLY tools
                model: "haiku" } } } })
  • Parallel = several Agent calls in ONE coordinator response. Spawning one per turn makes them run in sequence. Independent subtasks then finish in the time of the slowest one, not the sum of all of them.
  • description is routing. The coordinator reads it to decide which agent to use, so write it like a Lesson 2 tool description: purpose, inputs, when to use it.
  • Omit tools and the subagent inherits every tool. Always pass an explicit list.
Exam answer vs current reality

Exam (1.3)

"The Task tool as the mechanism for spawning subagents, and the requirement that allowedTools must include "Task"." Subagents are implied to be one level deep.

SDK today (v0.3.289)

It's the Agent tool in tool_use blocks, but Task in the system:init list, and "Task" is still accepted. allowedTools means auto-approve. In our test the coordinator spawned with allowedTools: [], and what it needs is Agent in tools. Subagents run in the background by default and can spawn their own subagents (default depth 3).
On the exam, answer "allowedTools includes Task". In real code, keep spawning in the coordinator only: that's what hub-and-spoke means.Subagents docs → Detect subagent invocation and Cap subagent depth.

4 · Scoped tools (2.3)

Giving an agent 18 tools instead of 4–5 makes its tool choice less reliable. An agent that has tools outside its role tends to misuse them: the guide's example is a synthesis agent running web searches.

PatternIn the lab
Role-scoped tool setssearcher → web_search · doc-analyst → list_documents, load_document · synthesizer → verify_fact
A constrained tool in place of a generic oneload_document(doc_id) opens only documents in the approved library, unlike a generic fetch_url
A scoped cross-role tool for frequent needsverify_fact handles the 85% of quick checks. Deep checks still go back through the coordinator (sample Q9)

5 · Coordinator prompts: goals and criteria, not procedures

Task statement 1.3 asks for coordinator prompts that "specify research goals and quality criteria rather than step-by-step procedural instructions". A numbered procedure fixes the shape of the decomposition in advance. Goals let the coordinator adapt to what it finds. Anthropic's version: each subagent needs "an objective, an output format, guidance on the tools and sources to use, and clear task boundaries."

✗ Step 1: pick the three most important subtopics. Step 2: ask the searcher about each, one at a time.
✓ Coverage: span the full breadth of the topic, one distinct area per subagent, no overlap.
  Proportion: a single fact needs one searcher. Speed: spawn independent subagents in ONE response.
  Subagents don't inherit your context: pass constraints and complete findings. Check for gaps; re-delegate.

8 · Scenario check

Ten new items, then six spaced-review items: three from Lesson 3 and three from Lesson 2. Commit to an answer before you click.

A research system on "health effects of social media on teenagers" produces reports about anxiety, depression and sleep, but never covers physical activity, body image or any positive effects. Each subagent's output is accurate. The coordinator's log shows three subtasks: anxiety, depression, sleep. What is the root cause?
  1. The search subagent's queries are too short to surface the other areas
  2. The synthesis subagent drops any findings that don't fit its outline
  3. The coordinator's decomposition is too narrow for the breadth of the topic
  4. The document subagent has no access to papers on the missing areas
The log shows that the missing areas were never assigned. The subagents did what they were given, and the gap is in what they were given (sample Q7's pattern). A, B and D blame agents that are working correctly within their scope.
Searchers return findings with URLs and dates, but the synthesis subagent's report has no citations. The coordinator's call to it says "Write the report based on the research so far." What is the most effective fix?
  1. Tell the synthesis subagent to look up sources for its claims itself
  2. Pass the full findings as structured data with source metadata in its prompt
  3. Turn on shared memory so the synthesis subagent can read the findings
  4. Switch the synthesis subagent to a larger model that cites more often
Subagents don't inherit the coordinator's context, so "the research so far" means nothing to the synthesizer. The fix is to put the complete findings in its prompt, with content kept apart from metadata (claim, evidence, URL, date) so attribution survives. A re-does the research in the wrong agent, C doesn't exist, and D doesn't change what the synthesizer can see.
A coordinator spawns four independent search subagents, one per turn, waiting for each result before the next. Research takes four times as long as the slowest single search. What change cuts latency most directly?
  1. Have the coordinator emit all four Agent calls in a single response
  2. Merge the four searches into one subagent with four times the budget
  3. Give each subagent a lower max-turns limit so each search ends sooner
  4. Cache search results so that repeated queries are answered instantly
Several Agent tool calls in one coordinator response run in parallel, so total time approaches the slowest subagent's time, not the sum. B loses the parallelism, C trades away quality, and D only helps with repeated queries.
A user asks for research "limited to EU regulation". The final report mixes US and EU material. The coordinator's prompts to the searchers say "Research AI copyright rules." Why did this happen?
  1. The searchers' web index ranks US sources above EU sources by default
  2. The synthesis subagent added US material to make the report complete
  3. Subagents only read the first user message when they have a long task
  4. Subagents don't inherit context, and the coordinator dropped the EU limit
A subagent sees only its own system prompt and the Agent prompt. The constraint was in the coordinator's context and never reached the searchers. The fix is to repeat user constraints in every subagent prompt. C is invented: subagents don't see the user's messages at all.
Your synthesis subagent has access to all 18 tools in the system. It often starts fresh web searches in the middle of a synthesis and sometimes picks the wrong tool for simple checks. What should you do?
  1. Add a rule to its prompt saying that it must never search the web
  2. Limit it to the tools its role needs, plus a scoped fact-check tool
  3. Add a routing classifier that picks the right tool for each request
  4. Rewrite all 18 tool descriptions so they are longer and more detailed
Too many tools reduces selection reliability, and tools outside a role invite misuse. Scope the tool set to the role, and add a narrow cross-role tool for the frequent need. A is probabilistic, C over-engineers, and D still leaves 18 choices.
A document-analysis subagent has a generic fetch_url tool. It sometimes fetches unrelated pages and pages from untrusted domains. What is the best tool-design change?
  1. Ask the subagent in its prompt to fetch only the documents it needs
  2. Log every fetch and review the logs at the end of each week for misuse
  3. Replace fetch_url with load_document that validates document sources
  4. Give the subagent a second tool that checks a URL before each fetch
The guide's 2.3 skill: replace a generic tool with a constrained one that enforces valid inputs. A relies on the prompt, B detects misuse only after it has happened, and D adds a choice the agent can skip.
The synthesis agent often needs quick checks of dates and figures. Each check goes back through the coordinator to the search agent, adding 2–3 round trips. 85% of checks are simple and 15% need real investigation. What is the best approach?
  1. Give synthesis a scoped verify_fact tool; route deep checks via coordinator
  2. Give the synthesis agent every web search tool the search agent has
  3. Batch every check and send the batch to search after synthesis ends
  4. Have the search agent pre-cache extra context around every source
This is sample Q9. A scoped cross-role tool covers the frequent simple case, and complex cases still go through the hub. B brings back cross-role misuse, C delays every check, and D guesses at what synthesis will need.
For "What year was the WGA founded?", your coordinator still runs web search, document analysis, synthesis and report generation, taking 90 seconds. What should change?
  1. Run all four subagents in parallel so the full pipeline finishes faster
  2. Have the coordinator assess the query and invoke only the agents it needs
  3. Add a cache in front of the pipeline so that repeated questions are free
  4. Use a smaller model for every subagent when the question looks short
Task 1.2: coordinators should "dynamically select which subagents to invoke rather than always routing through the full pipeline". A single fact needs one searcher. A, C and D tune a pipeline the question doesn't need.
Your coordinator prompt is 14 numbered steps that say which subagent to call, with which query, in which order. When early results point somewhere unexpected, the system can't adapt. What does the guide recommend?
  1. Add more numbered steps to cover each of the unexpected branches
  2. Move the procedure into code and remove the coordinator's discretion
  3. State research goals and quality criteria instead of a fixed procedure
  4. Let each subagent rewrite the procedure when its results look unusual
Task 1.3: specify "research goals and quality criteria rather than step-by-step procedural instructions, to enable subagent adaptability." A can never cover every branch, B removes the adaptivity this task needs, and D breaks hub-and-spoke control.
Which two are reasons to route all subagent communication through the coordinator rather than letting subagents message each other? (Select 2)
  1. One place to observe and trace every exchange between agents
  2. Subagents then share one context window, so they can read each other's work
  3. Consistent error handling and recovery decisions in one place
  4. It removes any need to pass findings explicitly in subagent prompts
  5. Each subagent can then use the full tool set without causing conflicts
The guide's 1.2 reasons are observability, consistent error handling and controlled information flow. B and D get context isolation backwards: routing through the hub is exactly why the coordinator has to pass findings explicitly. E contradicts scoped tool access.
Policy says customer data exports need manager approval. The prompt states this clearly, but an audit finds 2% of exports ran without approval. What is the proportionate fix?
  1. Repeat the approval rule at both the start and the end of the prompt
  2. Add few-shot examples of the agent asking for approval before exports
  3. Block export_data in a PreToolUse hook until an approval is recorded
  4. Have the agent rate its confidence that approval exists before exports
A compliance rule with a measured skip rate needs deterministic enforcement: a prerequisite gate. A and B are still probabilistic, and D relies on self-reported confidence. Lesson 3, reference.
"This is useless, I've been trying for ages!" writes a customer who wants to change a delivery address. The change is routine, and they haven't asked for a person. What should the agent do?
  1. Escalate to a human right away because the customer is clearly upset
  2. Acknowledge the frustration and offer to make the change right now
  3. Ask the customer to rate their frustration before choosing what to do
  4. Make the change silently and avoid mentioning the customer's tone
Frustration alone is not a trigger. Acknowledge it, resolve the issue, and escalate only if they ask for a human. A treats sentiment as complexity, C is absurd, and D skips the acknowledgement.
Your returns tool reports status: 4 and created: 1790864520. The agent sometimes tells customers a return is "pending" when 4 means "refunded", and it misreads dates. Where should the fix go?
  1. A system prompt table that maps each status code and explains epoch time
  2. A PostToolUse hook mapping codes to labels and epochs to ISO 8601
  3. A PreToolUse hook that asks the returns tool for a more readable format
  4. A new decode_status tool that the agent calls whenever it sees a code
Task 1.5: normalise heterogeneous formats in a PostToolUse hook, before the model reads the result. A and D still depend on the model converting correctly every time. C intercepts the call, but the problem is in the result. Lesson 3, reference.
An agent has search_orders ("Searches orders") and get_invoice ("Gets invoice data"). It often calls get_invoice when customers ask about order status. What is the proportionate first step?
  1. Add a routing classifier that picks the tool before the agent runs
  2. Merge both tools into a single order tool with a mode parameter
  3. Add ten few-shot examples showing which tool fits each question
  4. Expand both descriptions: purpose, inputs, returns, when not to use
Minimal descriptions are the root cause of misrouting (sample Q2). Fix the descriptions first: what the tool does, input formats, what it returns, and when to use the sibling tool instead. A, B and C are heavier changes made before the cheap root-cause fix. Lesson 2, reference.
One analyze_document tool is used to pull figures, write summaries and check claims against the source. The agent's inputs to it are inconsistent and outputs are hard to use. What tool-design change fits best?
  1. Split it into purpose-built tools, one per job, each with its own schema
  2. Keep one tool and add a free-text "task" field describing what to do
  3. Keep one tool and lengthen its description to cover every use case
  4. Keep one tool and return all three outputs together on every call
A generic tool with many jobs should be split by purpose (e.g. extract_data_points, summarize_content, verify_claim_against_source). Then each tool has a clear contract and selection is unambiguous. B and C keep the ambiguity, and D wastes context. Lesson 2.
The payments API times out. Your MCP tool returns isError: true with the text "Operation failed". The agent sometimes retries forever and sometimes tells customers their card was declined. What should the tool return?
  1. A JSON-RPC protocol error so the client knows the tool call failed
  2. A success result with an empty payment record and no error flag set
  3. isError with category transient, isRetryable true and a clear message
  4. isError with category business so the agent escalates to a human
A uniform "Operation failed" hides what the agent needs to decide. A timeout is transient and retryable, so retry a bounded number of times, then say it's temporary. A uses the wrong channel (protocol errors are for malformed requests). B disguises a failure as success. D mislabels it, which causes needless escalation. Lesson 2.

The agentic loop

stop_reason is the only reliable signal for whether the agent should keep going

Warm-up: before reading, predict
You already run Claude tool loops. Write down (on paper, not in your head) the three loop-termination anti-patterns you think the exam lists, and what Claude returns under tool_choice: {"type":"any"} when asked to "explain first, then call the tool". Check yourself against §2 and §4.

1 · The loop

A Claude agent is a while loop over one endpoint. Each iteration you send the whole conversation, read stop_reason, and act on it:Handling stop reasons, Anthropic Docs.

Three mechanics matter, and the exam probes all three:

  1. Append the assistant turn as-is. Push response.content unchanged. On current models it can contain thinking blocks you must not drop or edit.
  2. Return one tool_result per tool_use id, all in a single user message. The results go in the message immediately after the assistant turn, and all tool_result blocks come before any text in it. Text first returns a 400.Handle tool calls: shape {type, tool_use_id, content, is_error?} and the ordering rule. Splitting parallel results across several messages teaches Claude to stop calling tools in parallel.Parallel tool use.
  3. Failures are results too. If a tool throws, return a tool_result with is_error: true and the message. Never skip it, because a missing result is a 400 and gives Claude nothing to reason about.

Also: who chooses the next step? In an agent, Claude does, based on the tool results now in context. A hard-coded tool sequence is a workflow. That's a valid design, but it isn't what 1.1 means by "model-driven decision-making".Building Effective AI Agents, Anthropic: the workflows vs agents distinction.

2 · Three ways to stop the loop wrongly

The guide names these exact anti-patterns (1.1 skills). Each one bases the stop decision on something other than stop_reason:

Anti-patternWhy it breaks
Parsing natural language ("I'm done", "Final answer:")Wording isn't a protocol. It's brittle across prompts and models, and it ignores the structured signal you already have.
An iteration cap as the primary stopIt cuts off legitimate long tasks and lets broken loops run up to the cap. A cap is fine as a backstop; the exam wording is "as the primary stopping mechanism".
"Has text content → done"Claude often emits text alongside tool_use ("Let me look that up…"). Text in the response doesn't mean the turn is finished.
Exam heuristic Read "iteration cap" options carefully. "Cap as a safety net, terminate on end_turn" is fine. "Rely on a cap to end the loop" is the anti-pattern.

Production reality: more than two stop reasons

The guide only tests tool_use and end_turn, but a real loop must handle the rest explicitly rather than looping forever on them:

stop_reasonMeaning → action
max_tokensOutput was truncated, and a tool_use block may be incomplete. Retry with a higher limit.
pause_turnA server-tool loop hit its iteration limit. Send the assistant content back unchanged to continue.
refusalClaude declined. Read stop_details (null for every other reason).
stop_sequenceOne of your stop_sequences fired.
model_context_window_exceededThe context window is full. Treat the output as truncated.

3 · tool_choice

ValueBehaviourExam use
{"type":"auto"}Claude may call a tool or reply with text. Default when tools are given.Normal agent turns
{"type":"any"}Must call some tool; Claude picks which.Guarantee structured output when several extraction schemas exist and the document type is unknown
{"type":"tool","name":"x"}Must call tool x.Force extract_metadata first, then later steps in follow-up turns
{"type":"none"}No tool calls. Default when no tools are given.—

Two details the docs state outright:Define tools → Forcing tool use, Anthropic Docs.

  • Under any or tool, the API prefills the assistant turn, so Claude writes no explanatory text before the tool_use block, even if asked to. If you want both, use auto and ask for the tool call in the prompt.
  • disable_parallel_tool_use: true goes inside the tool_choice object. With auto it means at most one call; with any/tool, exactly one.
Exam answer vs current reality

On the exam

tool_choice: "any" guarantees a tool call, and forced {"type":"tool"} guarantees a specific one. Pick these answers.

In production today

Opus 5.5, Sonnet 5.5 and Fable 5.1 return a 400 for any/tool. The replacement is auto + strict: true on the tool, or structured outputs (output_config.format). Earlier models such as claude-opus-5 still accept forced choice; the lab uses one.

  1. Implement TODOs 1–4 in lab/01-agentic-loop/loop.ts, about 25 lines. Don't open solution/ yet. Run the default prompt and confirm you get tool_use → … → end_turn and a final answer.
  2. Observe the content blocks. In iterations that end in tool_use, which other block types appear next to the tool_use (text? thinking?). Predict before running. Whatever you see is evidence against the "text means done" anti-pattern.
  3. Parallel calls. Run "I'm jane@example.com. Compare orders 12345 and 12346." Do you get several tool_use blocks in one response? Check that your loop returns all the results in one user message.
  4. Errors are data. Run "Where is order 99999? I'm omar@example.com". The backend throws a 504. Confirm your loop sends is_error: true, and read how Claude explains it to the customer.
  5. Break the protocol on purpose. Temporarily put a text block before the tool_results in your user message, and read the 400. Then drop one tool_result from a parallel call and read that error. Revert.
  6. Forced tool choice. Set $env:MODEL="claude-opus-5"; $env:TOOL_CHOICE="any" and send "hi there!". A greeting gets a tool call. Now look at your logs: does the loop ever end? Explain why, then fix it so forcing applies only on iteration 1 and later turns use auto. This is exactly the guide's "force extract_metadata first, then process subsequent steps in follow-up turns".
  7. Reality check. Keep TOOL_CHOICE=any and switch $env:MODEL="claude-opus-5-5". Read the 400. That's the gap between the exam and current models.
  8. Preview of Lesson 3. Clear the env vars and run "I'm Jane Rivera, where's my latest order?". get_customer returns two Janes. Does Claude ask for another identifier, or guess? (The guide's 5.2 answer: it should ask.)
Step 6: why the forced loop never ends
Under any, every response must contain a tool call, so stop_reason is always "tool_use" and "end_turn" can never arrive. Only your backstop cap stops it. Fix: tool_choice: i === 1 ? forced : {type: "auto"}. Forced choice is a one-turn tool, not a loop setting.

5 · Scenario check

Exam format: one best answer unless the item says "Select N". Commit to an answer before you click.

Your support agent sometimes replies "Let me check that order for you" and then stops without ever calling lookup_order. The loop code exits as soon as a response contains a text block. What is the correct fix?
  1. Exit when the reply text contains a completion phrase such as "anything else?"
  2. Continue while stop_reason is "tool_use" and exit only on "end_turn"
  3. Raise the iteration cap so the agent gets more turns to finish its work
  4. Instruct Claude in the system prompt to never emit text before tool calls
Claude often emits text alongside a tool_use block, so "text present" doesn't mean the turn is complete. stop_reason is the structured signal. A is the natural-language-parsing anti-pattern, C misreads the cause, and D is fragile prompt compliance aimed at the wrong signal.
After lookup_order runs successfully, Claude's next response asks the customer for the order number again, as if the lookup never happened. Your loop executes tools correctly and logs their output. What is the most likely cause?
  1. The tool description for lookup_order is too short to be understood
  2. tool_choice is set to "auto" instead of forcing lookup_order to run
  3. The tool results are not appended to the messages sent next request
  4. The model's context window is exhausted by the order lookup output
The API is stateless: Claude only knows what is in messages. If you execute the tool but never append the assistant turn plus a user message with the tool_result, the next request has no record of the lookup. A and B affect whether the tool gets called, but it was called. D wouldn't produce a clean "ask again".
An extraction service receives documents that may be invoices, receipts or purchase orders. Each has its own extraction tool. Testing shows Claude sometimes answers in prose instead of calling any tool. The document type is not known in advance. Which tool_choice fits?
  1. {"type": "auto"} with a stronger instruction to use the tools
  2. {"type": "any"} so a tool must be called but Claude picks which
  3. {"type": "tool", "name": "extract_invoice"} as the safest default
  4. {"type": "none"} and parse JSON out of the text response
any guarantees a tool call while leaving the choice of schema to Claude, which matches "multiple schemas, unknown type" (4.3 skill). A still allows prose. C forces the wrong schema for receipts and POs. D gives up schema guarantees entirely. Reality note: on Opus 5.5 / Sonnet 5.5 you'd use auto + strict or structured outputs, but the exam answer is B.
A pipeline must run extract_metadata before any enrichment tool. You set tool_choice: {"type": "tool", "name": "extract_metadata"} on every request of the loop. Runs now hit the iteration cap and never finish. Why, and what fixes it?
  1. Forcing blocks parallel calls; add disable_parallel_tool_use to allow them
  2. The metadata tool output is too large; trim it before returning results
  3. Claude ignores forced tools when thinking is on; turn thinking fully off
  4. Forcing makes every turn a tool call; force turn one then switch to auto
Under forced choice, every response must call the tool, so end_turn never arrives. The guide's pattern: force the first step, then "process subsequent steps in follow-up turns" with auto. A is backwards (that setting limits parallel calls). B and C don't explain an endless loop.
Claude returns two tool_use blocks in one response: get_customer and lookup_order. How should your loop return the results?
  1. Send each tool_result in its own user message, in the order they ran
  2. Send both tool_results in one user message, before any text blocks
  3. Send only the first result and let Claude call the second tool again
  4. Merge both outputs into one text block in a single user message
Every tool_use id needs a matching tool_result, all in the single user message that immediately follows, with results before any text. A breaks the "immediately follows" rule and trains Claude away from parallel calls. C leaves an id unanswered (400). D drops the tool_use_id correlation.
A reviewer lists practices in a teammate's agent loop. Which three are the anti-patterns that the exam guide warns against? (Select 3)
  1. Ending the loop when the reply contains the phrase "task complete"
  2. Branching on stop_reason and returning tool results each iteration
  3. Relying on a 5-iteration cap as the main way the loop terminates
  4. Keeping a generous iteration cap purely as a runaway-loop backstop
  5. Treating any response with a text block as a finished final answer
A, C and E are the guide's three anti-patterns: NL parsing, cap as primary mechanism, and text-content-as-completion. D is the subtle distractor: a cap as a backstop is sound engineering. B is the correct loop.
With tool_choice: {"type": "any"}, you ask Claude to "briefly explain your reasoning, then call the right tool." Responses contain only a tool_use block with no explanation. What explains this?
  1. The tool descriptions are too long, so Claude skips the explanation step
  2. "any" disables thinking, so Claude cannot reason before acting
  3. Under "any" the API prefills the turn, so no text precedes tool_use
  4. The request needs disable_parallel_tool_use set to allow extra text
With any or tool, the API prefills the assistant message to force a tool call, so Claude emits no natural-language text before the tool_use, even when asked. To get both, use auto and request the tool call in the prompt.

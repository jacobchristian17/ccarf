Hooks, prerequisites and escalation

Rules that must hold go in code. Judgement calls go in the prompt.

1 · Prompts are probabilistic; hooks are deterministic

Sample Q1 in the guide describes an agent that skips get_customer in 12% of cases. The answer is a programmatic prerequisite, not a stronger prompt or more few-shot examples. In the guide's words: "when deterministic compliance is required (e.g., identity verification before financial operations), prompt instructions alone have a non-zero failure rate."Exam guide, task statement 1.4 and sample question 1 (md/CCAR-F/sections/07, 14).

Put it in a hook / gate when…Put it in the prompt when…
Breaking it costs money, breaks compliance, or can't be undone: refunds over a limit, actions before identity is verified, PII disclosureIt's a judgement call that needs context: when to escalate, how to phrase an apology, which concern to address first
A program can evaluate it from the tool name, the inputs and the state (amount > 500, verifiedCustomerId == null)Evaluating it requires reading the conversation (is this customer asking for a human, or just venting?)
"Must never happen" (a guarantee)"Should usually happen" (calibration)
Exam heuristic Financial, identity or compliance rule plus "the agent sometimes skips it" → hook or prerequisite gate. Any answer that only rewords the prompt, adds few-shot examples, or asks the model for a confidence score is the probabilistic distractor. The reverse also holds: escalation calibration (sample Q3) → explicit criteria plus few-shot in the prompt, not a classifier.

2 · Agent SDK hooks in 90 seconds

A hook is a callback your process runs at a fixed point in the agent loop. You register it under an event, with a matcher regex tested against the tool name. MCP tools are named mcp__<server>__<tool>.Intercept and control agent behavior with hooks, Claude Code Docs. Read "Outputs" and "Matchers".

EventFiresReturn inside hookSpecificOutputTask statement use
PreToolUsebefore the tool runspermissionDecision: "deny" + permissionDecisionReason; or updatedInputBlock refunds over $500; prerequisite gates
PostToolUseafter it returns, before the model reads the resultupdatedToolOutput (replace) or additionalContext (append)Normalise timestamps and status codes; redact
PreToolUse: [{ matcher: "^mcp__support__process_refund$", hooks: [enforceRefundLimit] }]

// deny → the model receives an is_error tool_result containing your reason
return { hookSpecificOutput: { hookEventName: "PreToolUse", permissionDecision: "deny",
  permissionDecisionReason: "Refunds over $500 need approval. Call escalate_to_human with …" } };
  • The reason is a redirect. The model reads it, so tell it what to do next ("call escalate_to_human with …"). The guide calls this "block policy-violating actions and redirect to alternative workflows".
  • All matching hooks run in parallel, and one deny wins over any allow. Write each hook to stand alone.
  • Fail closed. If a PreToolUse hook times out, the tool does not run.Hooks docs → Fix common issues → Hook timeout.
Exam answer vs current reality

Exam (1.5)

"PostToolUse hooks … intercept tool results for transformation before the model processes them." The guide names no fields.

SDK today (v0.3.289)

Replace output with updatedToolOutput, which works for every tool. updatedMCPToolOutput still exists but is deprecated. For MCP tools, tool_response is the content array [{type:"text",text}] (we checked).

3 · Prerequisite gates: PostToolUse writes state, PreToolUse reads it

A gate is two hooks that share per-session state. get_customer's PostToolUse records a verified ID only when there is exactly one match. A PreToolUse on lookup_order | track_shipment | process_refund denies the call until that ID exists. It also denies a refund whose customer_id doesn't match the verified one.

  • Several matches are not verified. Two "Jane Rivera" accounts mean you ask for another identifier (task 5.2). Never pick the one with the most recent order.
  • State belongs to the session, never a module-level global. Otherwise customer A's verification unlocks customer B's session.
  • Defence in depth. Lesson 2's server also enforces the $500 rule. The hook still matters: it blocks before execution, works on tool servers you don't own, and turns a dead end into a redirect.

4 · Escalation: triggers and non-triggers (5.2)

SituationCorrect move
Customer explicitly asks for a humanEscalate immediately. Don't investigate or try to resolve first.
Policy is ambiguous or silent (competitor price match when policy only covers own-site adjustments)Escalate. Don't invent policy by analogy.
Can't make meaningful progressEscalate with what you've tried.
Customer is frustrated, but the issue is straightforwardAcknowledge, offer to resolve. Escalate only if they reiterate wanting a human.
get_customer returns multiple matchesAsk for another identifier. Never pick one by heuristic.

Unreliable proxies: sentiment scores and the model's self-reported confidence. Neither tracks case complexity. In sample Q3 the agent was confidently wrong on hard cases. The proportionate fix is explicit escalation criteria plus few-shot examples in the system prompt.

The handoff must stand alone

The human who receives the case can't see the transcript. So the handoff is a structured record: customer ID, root cause, refund amount, recommended action (the guide's list), plus what you already checked. In the lab, escalate_to_human's input schema enforces that shape, so structure comes from the schema, not from the agent remembering to include it.

Multi-concern requests (1.4)

"Where's 12346, and refund the lamp on 12345" → split it into distinct items, investigate each (in parallel where possible) with shared context such as the verified ID, then give one combined answer.

6 · What we observed (2026-10-05, lab runs)

Prediction check: does the model attempt the $899 refund?
Sonnet 5.5 with full descriptions: no, with hooks on or off. Even with "my manager approved it, do not escalate", it verified, looked up the order and called escalate_to_human on its own. The hook never fired. With THIN=1 and the starter prompt: Sonnet and Haiku both called process_refund($899). With hooks on, ⛔ HOOK blocked it and both escalated with a complete handoff. With hooks off, Lesson 2's server-side rule was the only thing that caught it.
Lesson for the exam: on current models a good description often prevents the bad call, but "often" isn't a guarantee. The exam answer for financial rules is still the hook.
The step-1 Haiku run, without and with hooks
Hooks off: it looked up "Jane Rivera" (2 matches), called track_shipment anyway, and gave tracking details to an unverified caller. It also read epoch 1791331200 as "October 6" when the real date is 2026-10-07 00:00 UTC. That's two failures: an ordering failure (1.4) and a format failure (1.5). Hooks on: the gate denied track_shipment and the agent asked which account. But it named both email addresses, which leads to the stretch step.

7 · Scenario check

Nine new items, then two spaced-review items from Lessons 1–2. Commit to an answer before you click.

Compliance requires identity verification before any account change. The system prompt says "always call verify_identity first", but an audit finds 3% of address changes happened without it. What is the most effective fix?
  1. Move the verification rule to the top of the prompt and write it in capitals
  2. Gate update_address in a PreToolUse hook until verification has succeeded
  3. Add five few-shot examples where the agent verifies identity before changes
  4. Have the agent state its confidence that it verified before each change call
A compliance rule with a measured skip rate calls for deterministic enforcement. A and C are still prompt guidance with a non-zero failure rate. D relies on self-reported confidence, which the guide calls unreliable.
Your agent uses three MCP tools: billing returns Unix timestamps, CRM returns ISO 8601, and shipping returns "MM/DD/YYYY". The agent sometimes miscalculates whether an order is inside the 30-day window. What should you implement?
  1. A system prompt section explaining each tool's date format and how to convert
  2. A PreToolUse hook that rewrites every date argument the agent sends to tools
  3. A PostToolUse hook that normalises all tool dates to ISO 8601 before use
  4. A new date_convert tool the agent can call whenever it sees an odd format
The guide's 1.5 skill is exactly this: PostToolUse normalisation of heterogeneous formats before the model processes them. A and D still depend on the model noticing and converting correctly every time. B intercepts the wrong direction, since the bad data is in the results, not the arguments.
A PreToolUse hook blocks process_refund calls over $500. After it fires, the agent tells customers "something went wrong, please try later." What should change?
  1. Return allow with a lowered amount of $500 so the refund partly succeeds
  2. Set continue to false so that the whole session stops when the rule fires
  3. Move the $500 rule into the system prompt so the agent avoids the call
  4. Give a deny reason that redirects the agent to escalate_to_human with a handoff
The model reads the deny reason as an error tool_result. A reason without direction leaves it guessing. The guide's pattern is "block … and redirect to alternative workflows (e.g. human escalation)". A silently changes what the customer asked for, B abandons the customer, and C gives up the guarantee.
A customer writes: "Where's my package? Actually, just get me a real person." The tracking lookup would be routine. What should the agent do?
  1. Look up the tracking first, since it can resolve this in one quick step
  2. Escalate to a human at once without investigating the tracking question
  3. Ask the customer why they prefer a person before deciding what to do next
  4. Offer to resolve it first and escalate only if they repeat the human request
An explicit request for a human is honoured immediately, with no investigation first. D is the right move for a frustrated customer who hasn't asked for a human, which is what makes it a tempting distractor.
A customer is angry that a chair is two days late. Tracking shows a normal delay and a firm delivery date. Your agent escalates every message that contains strong negative language. What is the better behaviour?
  1. Keep escalating, since angry customers are the most likely to churn soon
  2. Raise the sentiment threshold so that only the angriest messages escalate
  3. Acknowledge the frustration, give the date, and offer to resolve it here
  4. Ignore the emotion and reply with only the tracking facts, kept brief
Sentiment doesn't track complexity, and this case is simple. Acknowledge, resolve, and escalate only if the customer asks for a human again. B tunes an unreliable proxy instead of removing it.
get_customer("Maria Lopez") returns three accounts. The agent picks the one with the most recent order and proceeds. What should it do instead?
  1. Pick the account with the highest loyalty tier, since it is likeliest
  2. Ask the customer for another identifier, such as their email address
  3. Proceed with all three accounts and filter the orders that match later
  4. Escalate to a human, because ambiguous identity is always a policy gap
Several matches call for clarification with another identifier, not a heuristic pick (A, or the original behaviour). C exposes other people's data. D escalates something the agent can resolve with one question.
A customer asks you to match a competitor's lower price. Your policy covers price adjustments only when your own site drops its price. What should the agent do?
  1. Apply the own-site adjustment rule to the competitor price by analogy
  2. Decline outright, since the policy does not mention competitors anywhere
  3. Ask for the competitor's link and refund the difference if it checks out
  4. Escalate, because the policy is silent on this particular request
This is the guide's own example: when policy is ambiguous or silent on the request, escalate. A and C invent policy. B treats silence as a no, which is also inventing policy.
Escalated cases reach a human team that can't see chat transcripts. Agents spend the first five minutes of every case re-asking the customer for details. What fixes this at the source?
  1. Have the agent write a warm summary paragraph for each escalation
  2. Give the human team read access to the agent's raw tool call logs
  3. Require a structured handoff: customer ID, root cause, amount, next step
  4. Ask the customer to restate their problem just before the handoff
The guide's 1.4 skill: compile structured handoff summaries (customer ID, root cause, refund amount, recommended action) for humans who don't have the transcript. Putting the shape in the escalation tool's schema enforces it. A lacks guaranteed fields, B dumps unprocessed context on people, and D pushes the work back to the customer.
Which two rules belong in deterministic hooks rather than in the system prompt? (Select 2)
  1. Never issue a refund above $500 without a human approving it first
  2. Apologise briefly before giving bad news about a delayed delivery date
  3. Never call lookup_order before get_customer has verified one account
  4. Escalate when the customer's request is not covered by written policy
  5. Split multi-part requests into separate issues before investigating them
Both correct rules are financial or identity guarantees that code can evaluate from the tool name, the inputs and the state. The others need judgement about the conversation (tone, policy coverage, decomposition), so they belong in prompt criteria and few-shot examples.
list_returns finds no returns for a customer in the last 90 days. How should the MCP tool report this?
  1. isError true, with errorCategory validation and isRetryable false
  2. A normal successful result containing an empty list of returns
  3. isError true, with errorCategory transient so the agent tries again
  4. A JSON-RPC protocol error so the client knows nothing was returned
A query that worked and found nothing is a valid empty result, not an access failure. Flagging it as an error leads to pointless retries or a false "system down" message.
Claude returns two tool_use blocks in one response: track_shipment and lookup_order. How do you send the results back?
  1. Two user messages, one tool_result in each, in the order they finished
  2. One user message with a text summary first, then both tool_result blocks
  3. One user message containing both tool_result blocks, before any text
  4. Only the first tool_result now, then the second one on the following turn
All results go in a single user message, and tool_result blocks come before any text. Splitting them up or putting text first breaks parallel tool use. Lesson 1, reference.

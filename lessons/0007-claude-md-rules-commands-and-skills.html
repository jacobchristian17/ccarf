CLAUDE.md, rules, commands and skills

Every Domain 3 configuration question comes down to two choices: who gets an instruction (just you, or everyone who clones the repo) and when it enters context (always, when a matching file is touched, or only when someone asks). Get both right and the rest follows.

1 · The CLAUDE.md hierarchy (3.1)

FileWho gets itWhen it loads
~/.claude/CLAUDE.md (user)Only you, in every project. Not in gitAt launch
./CLAUDE.md or ./.claude/CLAUDE.md (project)Everyone who clones the repoAt launch
./CLAUDE.local.mdOnly you, in this project. You add it to .gitignoreAt launch, after CLAUDE.md
packages/billing/CLAUDE.md (directory)EveryoneOn demand: the first time Claude reads, writes or edits a file under that directory
Managed policy (C:\Program Files\ClaudeCode\CLAUDE.md …)Everyone on the machine. It can't be excludedAt launch, first

The exam's favourite diagnosis: "a new team member isn't getting the instructions". The instructions are in someone's ~/.claude/CLAUDE.md, which never left their machine. The fix is to move them into the project file. The reverse failure is just as real: personal preferences committed to the project file reach every teammate. In the lab's starter config, a teammate's session recites "You alias pnpm test as t in your shell" back to them.

The files stack. They don't override each other. The docs: "All discovered files are concatenated into context rather than overriding each other", ordered from the filesystem root down, so the closer file is read last. If two files contradict each other, "Claude may pick one arbitrarily". The fix for a conflict is to remove it, not to rely on which file wins.Memory (CLAUDE.md): "Choose where to put CLAUDE.md files" and "How CLAUDE.md files load". Task statement 3.1, md/CCAR-F/sections/09.

@import keeps it modular

# packages/billing/CLAUDE.md
Owned by the billing team. Cite the rule source for every tax change.

@../../docs/standards/money.md        # relative to THIS file, not the working directory
  • Relative paths resolve from the importing file. Absolute paths work too. Imports can nest up to four hops.
  • An @path inside a code span or fenced block is ignored, so code examples don't trigger imports.
  • The first time a project imports a file from outside the working directory, Claude Code asks for approval. If you decline, the dialog doesn't come back.
  • Import selectively. Each package imports the standards its maintainers know apply to it, not every standards file. An import is expanded into context in full, so a lazy "import everything" costs as much as pasting everything in.

2 · .claude/rules/ and path scoping (3.3)

Split a monolithic CLAUDE.md into one focused file per topic: testing.md, api-conventions.md, deployment.md. A rule file has two modes:

# no frontmatter → loads at launch, same priority as .claude/CLAUDE.md (just tidier)

---
paths:
  - "**/*.test.*"            # YAML list of quoted globs (a comma-separated string also works)
---
# Tests
- Vitest. Import test/expect explicitly; no globals.

A paths: rule stays out of context until Claude touches a matching file. That saves tokens, and it also keeps irrelevant conventions out of the model's attention. Why globs instead of a directory CLAUDE.md? A directory file is tied to one directory. Test files sit next to the code they test, in every directory, so only a file-type glob (**/*.test.tsx) catches all of them. That's sample Q6. The lab's starter config shows the failure: its test conventions live in src/api/CLAUDE.md, so tests in src/web/, src/lib/ and packages/billing/ never get them.

This repo already has one. .claude/rules/test-output.md is scoped to lab/**/check.ts and lab/**/*.test.ts. When I wrote lab/07-team-config/check.ts for this lesson, it loaded on its own, which is why the grader prints green ✓ and red ✗ like the other six.

3 · Commands and skills (3.2)

Project (shared through git)Personal (just you)
Command: one Markdown file → /name.claude/commands/review.md~/.claude/commands/review.md
Skill: a directory with SKILL.md plus optional files.claude/skills/impact-scan/SKILL.md~/.claude/skills/my-impact-scan/SKILL.md

Your own machine shows both columns. You have personal commands in ~/.claude/commands/ (app-engineer.md, project-manager.md …) and personal skills in ~/.claude/skills/. The tutor skill that produced this lesson's outline uses argument-hint and allowed-tools. None of them reach a teammate.

SKILL.md frontmatterWhat it does
descriptionWhen to use it. Claude reads the description to decide whether to invoke the skill. The body loads only when it's invoked
context: forkRuns the skill in a subagent that doesn't see your conversation. Only its final result comes back. Use it for verbose output (codebase analysis) or exploratory output (brainstorming) that would clutter the main session
agent: ExploreWhich subagent the fork runs in: Explore, Plan, general-purpose (the default), or one from .claude/agents/
argument-hint: "<symbol or file>"Shown when someone types /impact-scan with no arguments, as a prompt for what to pass. The body reads them as $ARGUMENTS, $0, $1 …
allowed-toolsExam: "restrict tool access during skill execution". Today: see the callout below
disable-model-invocation: trueOnly a person can run it, for workflows with side effects (deploy, commit)

Skill or CLAUDE.md? CLAUDE.md is always loaded, so it's for universal standards that apply to every task. A skill loads on demand, so it's for a task-specific workflow that runs sometimes. A 15-line "how to do an impact scan" procedure in CLAUDE.md costs context in every session and dilutes attention on the rules that always apply. As a skill, it costs one description line until someone needs it. (A path rule is the third option: conventions that depend on which file is being touched.)

Personal variants get a different name. If a skill name exists at both levels, the personal one wins ("enterprise over personal, and personal over project"). A personal impact-scan would quietly shadow the team's version on your machine, so you'd be testing something your teammates don't run. Call yours my-impact-scan.Skills: "Where skills live", "Frontmatter reference", "Run skills in a subagent", "Pre-approve tools for a skill". Task statement 3.2.

Exam answer vs current reality

Exam (3.1–3.3)

Commands live in .claude/commands/, skills in .claude/skills/. allowed-tools restricts what a skill can use ("limiting to file write operations to prevent destructive actions"). Path rules load "only when editing matching files". /memory verifies which memory files are loaded.

Today (CLI 2.1.290)

Commands have been merged into skills: .claude/commands/x.md and .claude/skills/x/SKILL.md both create /x, and on a name clash the skill wins. allowed-tools pre-approves tools for that turn: "It does not restrict which tools are available". The restricting field is disallowed-tools. Path rules trigger on Read, Write or Edit. /memory is mostly an editor; use /context for what's loaded now.
On the exam, answer in the exam's terms: allowed-tools is the restriction mechanism, and "editing" is when path rules load. In real configs, put the read-only list in allowed-tools and the dangerous tools in disallowed-tools. §5 shows why. Memory ("Path-scoped rules trigger when Claude uses the Read, Write, or Edit tool on a file matching the pattern"). Hooks → InstructionsLoaded.

5 · What we observed (2026-10-06, Haiku 4.5, CLI 2.1.290, SDK v0.3.289)

Prediction check (a): does a Read load a path rule?
Yes. load src/web/InvoiceList.test.tsx with no edit loaded two rules: testing.md (**/*.test.*) and frontend.md. The second was a surprise: src/web/**/*.tsx also matches InvoiceList.test.tsx, so overlapping globs stack. Each rule loads once per session. In map, testing.md fired on the first test file and didn't fire again. With edit terraform/main.tf, the rule loaded on the Read that came before the Edit. The exam's "when editing" is true, but a read is enough.
map: starter vs reference
Starter: 514 tokens of CLAUDE.md at startup, including Terraform, React and billing rules, in every session. After that, only src/api/CLAUDE.md loaded (nested_traversal, on src/api/invoices.ts). So test conventions reached the API tests and none of the other three test files.
Reference: 185 tokens at startup. Then api.md loaded on invoices.ts, frontend.md on InvoiceList.tsx, testing.md on the first test, packages/billing/CLAUDE.md on tax.ts with docs/standards/money.md right after (include), and terraform.md on main.tf. Each rule loaded when it was needed and not before.
Tooling note: the SDK hook never reported session_start for the root CLAUDE.md, although the model could quote it with no tools. The runner reads the startup list from getContextUsage().memoryFiles, the same data /context shows.
ask: what a teammate's session knows at startup
Starter: it listed all three Terraform rules and then "Your personal answer style: Keep answers terse… You alias pnpm test as t in your shell", in a session meant to be a teammate's. Reference: Terraform: none. Personal style: none. It also noted that topic rules exist in .claude/rules/ but weren't loaded yet, which is correct.
skill: context: fork vs inline
Forked (reference): /impact-scan toCents ran the skill in an Explore subagent: 5 tool calls there, 0 tool calls and 0 turns in the main thread, and a ~750-character summary back. When the prompt starts with the slash command, the CLI runs the forked skill before the main model takes a turn.
Inline (starter, or NOFORK=1): 5–6 Grep/Read calls in the main thread, with 1.2k–2.9k characters of raw tool output left in the main context. That's tiny on an 8-file fixture. On a real monorepo, a 40-file impact scan would leave all of its output in your session.
Gotcha: in a forked skill, everything after /impact-scan becomes $ARGUMENTS. "…and then save it to IMPACT.md" went to the read-only Explore agent, which replied that it was in read-only mode. That's why guard runs the skill inline. And in non-interactive runs, the Skill tool itself needs permission: when it was denied, Haiku quietly did the scan by hand in the main thread.
Prediction check (b): does allowed-tools stop a write?
No. With allowed-tools: Read, Grep, Glob and nothing else, the skill ran, then called Write(IMPACT.md), and the file was created. With disallowed-tools: Write, Edit, Bash added, Write was denied, and the model tried Bash (cat > IMPACT.md) as a workaround, which was also denied. Two lessons: allowed-tools grants permissions and doesn't remove tools, and a deny list has to cover the workaround tools too (Bash can write files).

A four-phase codebase-audit pipeline is killed by a deploy halfway through phase 3. On restart it reruns phases 1 and 2, and phase 4's planner never sees what phase 3 found. What fixes both problems?

  2. Store the coordinator's transcript and resume that on restart
  3. Merge the four phases into one agent that runs from start to end
  4. Have each phase export state, and resume from a loaded manifest

Every pull request in your repo must pass the same four checks in order: license headers, then secrets scan, then dependency diff, then changelog entry. Which decomposition fits best?
  1. A coordinator that decides which checks each pull request needs
  2. A fixed sequential pipeline with one step for each of the checks
  3. One open-ended prompt asking the agent to review the pull request
  4. A dynamic plan the agent builds after mapping each pull request

A pricing-research subagent can't reach one of its three data sources because of an authentication error. It returns {"status": "error", "message": "failed"}, and the coordinator gives up on the whole subtopic. What should the subagent have returned?

Two sources give different market-size figures for the same year: $4.1B from an analyst report and $6.3B from a trade association. The synthesis agent reports "about $5B". What should it have done?
  1. Pick the figure from whichever source is the more authoritative
  2. Report the average and add a footnote saying the sources disagree
  3. Drop the market-size claim, since the evidence is inconsistent
  4. Report both figures, each with its source, and flag the conflict
When sources conflict, keep both values with their attribution and flag the conflict. The reader, or a later step, can then judge methodology. A makes the choice silently. B produces a number that no source supports. C throws away real evidence. Lesson 5.
A 40-turn support conversation starts with the customer's account number, refund amount and order date. By turn 35, the agent's summaries of the case describe the refund as "a recent purchase" with no amount. What is the best fix?
  1. Keep a persistent case-facts block in context, outside summaries
  2. Ask the customer to repeat the key details every ten turns or so
  3. Summarise the conversation more often, so that fewer facts are lost
  4. Use a model with a larger context window for long conversations
Progressive summarisation loses exact values. Extract transactional facts (amounts, dates, IDs) into a structured block that is carried forward and never summarised. B pushes the problem onto the customer. C makes the loss worse. D delays the problem. Lesson 5, reference.

Secrets: ${VAR} expansion

{
  "mcpServers": {
    "tally-index": {
      "command": "node",
      "args": ["${TALLY_TOOLS_DIR}/tally-index.mjs"],
      "env": { "TALLY_INDEX_TOKEN": "${TALLY_INDEX_TOKEN}" }   # each developer's own token, from their shell
    }
  }
}
  • Expansion works in command, args, env, url and headers. ${VAR:-default} gives a fallback. Never put a real token in the default, because the default is committed too.
  • A literal token in .mcp.json is in every clone and in git history. Deleting it later doesn't undo that, so rotate the token.
  • An unset variable doesn't stop the server. The docs: "the config still loads … and uses the unexpanded ${VAR} text as-is", with a warning in claude mcp list. Your server receives the string ${TALLY_INDEX_TOKEN} as its token. A server should recognise that and say so in its error. The lab's server does.Same page, "Environment variable expansion in .mcp.json". Verified 2026-10-06.

Community server or your own?

For a standard integration (Jira, GitHub, Sentry, Postgres), use an existing community or vendor server. Someone else maintains the API mapping and the auth. Build a custom server only for workflows that are specific to your team: an index of your codebase's own aliases, or your internal deploy process. "We wrote our own Jira server" is a distractor unless the scenario gives a reason.

2 · Getting the agent to use the right tool (2.4)

The exam's scenario: the team's MCP server has a tool that does more than a built-in (it resolves aliases, or knows the schema), and the agent still reaches for Grep. The exam's answer is the tool description. A tool called find_references described as "Find references." gives the model no reason to prefer it over a tool it knows well. A good description says:

  1. what it does that the built-in can't ("follows re-export aliases and wrapper functions that text search misses"),
  2. when to use it, and that it should be used instead of Grep for that question,
  3. what it takes as input and what it returns (file:line per call site),
  4. what it doesn't cover ("not comments or strings: use Grep for those").

That's the Lesson 2 rule (descriptions are the model's main signal for choosing a tool), applied across the MCP/built-in boundary.

Resources: a catalog instead of exploration

Tools do things. Resources expose content the client can read. To answer "where's the VAT rate stored?", an agent with only list_tables and describe_table has to explore: list, then describe one table, then another. A tally://schema resource gives it the whole catalog in one read. Use resources for catalogs like issue summaries, documentation trees and database schemas, which "give agents visibility into available data without requiring exploratory tool calls".MCP spec: Resources ("exposing data that provides context"). In Claude Code the agent reads resources through its ListMcpResourcesTool / ReadMcpResourceTool tools (observed in the lab).

server.registerResource("schema", "tally://schema", {
  title: "tally database schema",
  description: "Every table with all columns, types and notes. Read this before describing tables.",
  mimeType: "text/markdown",
}, async uri => ({ contents: [{ uri: uri.href, mimeType: "text/markdown", text: schemaMarkdown() }] }));

4 · Plan mode vs direct execution (3.4), and iterating (3.5)

Plan mode firstExecute directly
Large-scale or multi-file changes; library migrations touching 45+ files; architectural decisions; several valid approaches with different infrastructure needsWell-understood changes with a clear scope: a one-file bug fix with a clear stack trace; adding one date-validation conditional

Plan mode is read-only. Claude explores and proposes, and nothing changes until you approve, so a wrong approach costs a re-plan instead of a rework. Enter it with Shift+Tab, /plan, claude --permission-mode plan, "defaultMode": "plan", or SDK permissionMode: "plan". Combine the two: plan the migration, approve the plan, then let it execute. For the verbose discovery phase of a long task, the read-only Explore subagent keeps file dumps out of the main context and returns a summary (the context: fork + agent: Explore you used in Lesson 7).Permission modes (plan mode) and Subagents ("Explore": read-only, three thoroughness levels). 6 · What we observed (2026-10-06, Haiku 4.5, CLI 2.1.290, SDK v0.3.289)

Scopes: what servers reports
Each connected server comes back with a source. tally-index was project (read from .mcp.json with settingSources: ["project"], with no approval prompt in the SDK), and the personal server was the user-level stand-in. All five MCP tools were available in the same session. Two tooling notes. strictMcpConfig: true (which the L4–L7 labs used) drops .mcp.json entirely. Without it, your claude.ai connectors join too (80 extra tools here), so the runner hides them from its report.
Prediction check (b): the unset variable
With $env:NOTOKEN="1", the server still showed as connected. Claude Code passed the literal text ${TALLY_INDEX_TOKEN} as the token, just as the docs say. Before we added a check, our server accepted it, because the string isn't empty. Now it returns a permission error that names the cause, and the agent told the user to set the variable in their shell. The lesson for server authors: treat ${…} as "missing", not as a token.
Prediction check (a): does a better description win over Grep?
Not with tool search on. "Who calls toCents?" on the starter: 23 calls (Grep×7, Read×13, Glob×3), all 5 caller files found, find_references never called. With the full reference description: 10 calls (Grep×5, Read×5), and still no MCP tool. The model saw only the tool's name in the deferred list and never searched for it.
Adding server instructions ("for who-calls questions use find_references instead of Grep…") gave 2 calls (ToolSearch → find_references), with 5/5 files, twice in a row.
With ENABLE_TOOL_SEARCH=false, even the starter's "Find references." got used in 1 call. Once the tool is in the prompt, its self-explanatory name is enough for this question. Descriptions earn their keep when names are ambiguous or the tool needs input-format guidance (Lesson 2).
The resource: schema
Without the resource: ToolSearch → list_tables → describe_table(line_items) → describe_table(tax_rates), which is 3 server calls. With it: one ReadMcpResourceTool(tally://schema) read (the resource tool itself was deferred, so there was a ToolSearch first). On 4 tables the saving is small. The exploratory pattern grows with the catalog, though, and the single read doesn't.
Built-ins: edit on a duplicated line
Haiku Read the file, then made one successful Edit that changed only roundHalfEven. It widened old_string to include the function signature, which made the anchor unique. That's the first fix to try. Read + Write is the fallback the exam expects when no unique anchor exists. It then spent 11 more calls looking for tests to run. That's the L7 CLAUDE.md's "run pnpm test" rule at work in a session with no shell.

Context degradation in long sessions is handled by persisting findings outside the context (a scratchpad with exact references), along with subagents and /compact. A throws away the progress. C repeats instructions, not findings. D only postpones the problem. Lesson 6.
A single review pass over a 20-file pull request gives detailed comments on the first few files, superficial ones later, and misses a cross-file contract change. How should the review be restructured?
  1. Use one pass with a stronger instruction to review every file equally
  2. Run three identical full-PR passes, keeping only issues that all three report
  3. Run per-file local passes, plus a separate cross-file pass over their findings
  4. Review only the files with the largest diffs, skipping the smaller changes
Attention dilution across many files is fixed by decomposition: focused per-file passes for local issues, then an integration pass for data flow across files. A asks the same overloaded pass to try harder. B suppresses real issues that only some runs catch. D drops coverage on purpose. Lesson 6.

Error propagation and provenance

If a failure never reaches the coordinator, the coordinator can't recover from it. If a source never reaches the synthesizer, nobody can check the claim. This lesson is about what has to survive each handoff.

1 · Four ways to report a failure (5.3)

Sample Q8 is the template. A web-search subagent times out. How should that failure reach the coordinator? The guide rejects three of the options, and each rejection is a pattern you will see again.Sample question 8, md/CCAR-F/sections/14. Task statement 5.3, md/CCAR-F/sections/11.

PatternWhat the coordinator seesVerdict
SuppressAn empty result marked as success✗ No recovery is possible, and the report looks complete when it isn't
Generic"search unavailable", sent after the subagent's own retries✗ The context is hidden: which query failed, what still worked, what to try next
TerminateNothing. A top-level handler kills the run✗ One failure throws away every other subagent's results
StructuredFailure type, attempted query, partial results, alternatives✓ The coordinator can retry a different query, try another source, or go ahead and annotate the gap

Note the division of labour. The subagent handles transient failures locally (retry once) and propagates only what it can't resolve. The coordinator owns the recovery decision, because it is the only agent that can see the whole plan. That is the hub-and-spoke argument from Lesson 4 again: consistent error handling happens in one place.

Exam heuristic When a question asks how a failure should flow, look for the option that carries context (type, what was attempted, partial results, alternatives) to the agent that decides. "Retry with backoff, then return a generic status" sounds robust, but it is the trap: the retries are fine, and the generic status is what's wrong.

2 · Access failure vs valid empty result

You met this distinction in Lesson 2 at the tool level (isError with errorCategory versus { results: [] }). Task 5.3 lifts it one level up, to the subagent's report:

StatusMeaningCoordinator's move
complete, findings > 0CoveredUse it
complete, findings = 0Valid empty result: the searches worked and nothing matchedReport "no matching sources". Don't retry it as if it were an outage
partialSome queries worked, and one failed after a local retryKeep the findings. Re-delegate once with an alternative, or annotate the gap
failedAccess failure: nothing could be retrievedRe-delegate once with an alternative, then proceed without it and annotate the gap

"We searched and found nothing" is evidence about the world. "We couldn't search" is evidence about your plumbing. If a report merges the two, the coordinator either retries real absences forever or treats outages as absences. The second is worse, because the final brief then states something false with confidence.

3 · Provenance: the claim–source mapping (5.6)

Attribution is lost at summarization steps, where findings get compressed and the mapping from claim to source is dropped. Every handoff in a multi-agent system is a potential summarization step: subagent → coordinator → synthesizer → final answer. The defence is structure that each hop must preserve and merge: { claim, evidence, source: { id, publisher, published, page } }. Anthropic's research system goes one step further and uses a dedicated CitationAgent pass "to identify specific locations for citations".How we built our multi-agent research system, process diagram section, and its Appendix on subagent outputs that "persist independently" to prevent "information loss during multi-stage processing".

  • Conflicting values from credible sources: keep both and annotate each with its source. Don't pick one, average them, or drop one. If a subagent finds a conflict, it should finish the analysis with both values included and let the coordinator decide how to reconcile them before synthesis.
  • Dates: require publication or collection dates in the structured output. Without them, "18% in 2024" and "31% in 2026" look like a contradiction when they are really a trend.
  • Methodological context: keep each source's own characterization. In the lab, "31% use AI in at least half their sessions" and "25% use AI regularly (n = 1,200)" measure different things. Collapse them to "about 28% use AI" and you've made up a number.
  • Report structure: keep well-established findings separate from contested ones, and include a coverage section. Render by content type: figures as tables, news as prose, technical findings as lists.

4 · The context budget between agents (5.1)

Task 5.1 includes several multi-agent skills. They come down to this: what crosses a handoff should be small, structured and ordered on purpose.

  • Return structured data, not reasoning chains, when the downstream agent has a limited context budget: key facts, citations, and where useful a relevance score. Anthropic's figure: a subagent "might explore extensively, using tens of thousands of tokens or more, but returns only a condensed, distilled summary of its work (often 1,000-2,000 tokens)."Effective context engineering for AI agents, "Sub-agent architectures".
  • Trim verbose tool output to the relevant fields before it accumulates. In the guide's customer example, an order lookup has 40+ fields and the task needs 5.
  • Position matters ("lost in the middle"). Models reliably use the beginning and end of a long input and may skip the middle. Put a key-findings or coverage summary at the top of aggregated input, and organise the details under explicit section headers. Anthropic's long-context guidance makes the same point about structure: long data first, the query at the end ("up to 30 percent" better), and each document wrapped with its source metadata.Prompting best practices → Long context prompting. The term "lost in the middle" itself comes from Liu et al. 2023 (arXiv:2307.03172). No Anthropic page uses it.
  • Require metadata from subagents (dates, source locations, methodological context), so the synthesizer can interpret the findings correctly.

The rest of 5.1 (a "case facts" block kept outside summarised history, and multi-issue state in customer sessions) belongs to the customer-support scenario and comes back in Lesson 11.

Exam answer vs current reality

Exam (5.3, 5.6)

The guide frames these as design choices: subagents return structured error context, the synthesis agent must preserve claim–source mappings, and you require dates in the output. The mechanism it names is the output format you ask each agent for.

SDK today (v0.3.289)

You can enforce it in code. A SubagentStop hook can validate the final report and return decision: "block" with the issues, and the subagent then fixes its report. A PreToolUse hook on Agent can return updatedInput to replace the synthesizer's prompt with a brief that code built. The lab uses both. Both are verified in our runs.
On the exam, pick the structured-output answer. In production, prompt for the structure, then validate it in code. That's the Lesson 3 rule again: deterministic enforcement where the stakes justify it. Lesson 10 makes this validate-and-retry loop the main topic.Hooks reference: SubagentStop decision control, and PreToolUse updatedInput.

6 · What we observed (2026-10-05, Sonnet 5.5 coordinator, Haiku subagents)

Starter files, OUTAGE=games: 82 s
The games searcher hit 3 timeouts and retried none of them. It reported partial with an error whose fields the starter's empty SubagentError schema had stripped, so the coordinator received error {}. That is the "generic status" anti-pattern, produced by an under-specified contract rather than a lazy model. Four other sectors were also marked partial, with nothing to say why. Sonnet still named the games gap ("timed out and were not retried"), but only because it read the raw report text. The final answer cited 0 source ids.

The remaining runs use the reference solution.

Prediction check: did the reports match the contract first time?
Often not. With OUTAGE=games, SubagentStop sent back 7 reports in one run. With FLAKY=1 it sent back 8. The most common faults were partial without an error object and a timeout recorded with attempts: 1 (R5: the searcher hadn't retried). After one retry most reports parsed. In two cases a report was still malformed (bad JSON, and an invalid status). The PostToolUse hook stored those as failed · unavailable instead of dropping them, so the coordinator saw a gap rather than silence. The prompt described the contract, and only the code enforced it.
Outage run (OUTAGE=games, creative): 131 s
Six researchers ran in parallel. The games searcher returned failed · timeout after 4 timed-out calls. The coordinator re-delegated once ("Games retry"), and an alternative query got through, giving partial · 1 finding (NPC dialogue). The brief injected into the synthesizer was 11,190 chars with all 12 source ids. Final answer: both 31% and 25% were kept, games was named as a gap with the reason (timeouts), and 12 sources were cited.
Not ideal: Haiku marked music, writing and film as partial · unavailable because it found nothing on lawsuits. That is a valid empty result labelled as an access failure, which is exactly the confusion 5.3 warns about. The contract can't catch it, because the model chose the wrong label, not an invalid one. The coordinator's final note still called it "a genuine absence … not a technical failure".
Valid-empty run (FLAKY=1, dance): 144 s
Dance came back as complete · 0 findings after six queries. The final answer said "no matches … a genuine absence", not unavailable. Theatre, whose retry report was malformed, was annotated as "a retrieval gap, not evidence of absence". The difference was preserved all the way to the user. On conflicts, Sonnet wrote that 31% and 25% "measure different things" and kept both, preserving the methodological context.
The last hop lost provenance. The coordinator rewrote the synthesizer's brief and changed [https://…] into "(Music Ledger, 2026-02-02)". The final answer cited 1 source id, against 11 in the brief. Publisher and date are still attribution, but the claim can no longer be traced to a URL. Every handoff is a summarization step (§3), including the last one. See stretch step 7.

7 · Scenario check

Ten new items, then six spaced-review items: three from Lesson 4 and three from Lesson 3. Commit to an answer before you click.

Your document-analysis subagent can't open two of five reports because of a permissions error on the file store. It currently returns {"status":"error"}, and the coordinator either restarts the whole research run or ignores the subagent. What should the subagent return?
  1. The same status, plus a log of every call, so a human can debug it later
  2. The three analysed reports as a normal success, without the two failures
  3. Failure type, the reports attempted, the partial results and alternatives
  4. An exception that bubbles up to a top-level handler and stops the research
Structured error context lets the coordinator decide whether to retry, try another source, or proceed with the partial results (sample Q8). A gives the coordinator nothing it can act on. B suppresses the failure, so the gap disappears. D terminates the whole workflow because of one subagent.
A searcher reports status: "failed" whenever a query returns zero results. For niche subtopics, the coordinator retries three times and then says the "search service was unavailable". What is the root cause?
  1. The coordinator's retry limit is too low for such niche topics
  2. A valid empty result is being reported as an access failure
  3. The search index needs more sources on the niche subtopics
  4. The searcher's queries are too narrow to return any results
Zero results from a search that worked is a valid empty result: "complete, no matching sources". Calling it a failure triggers pointless retries and a false explanation in the final report. A makes the waste worse. C and D might be true, but they don't explain why "unavailable" was reported.
A subagent sends every transient 503 from its search API straight to the coordinator. The coordinator spends most of its turns handling errors that would have cleared on a retry. What is the best change?
  1. Have the coordinator ignore every error that it gets from a subagent
  2. Retry indefinitely inside the subagent until every query succeeds
  3. Return an empty result as a success whenever the API returns a 503
  4. Retry transient errors locally; send only unresolved ones, with context
Subagents should recover locally from transient failures and propagate only what they can't resolve, including what was attempted and any partial results. A loses real failures, B can hang forever, and C suppresses the error.
One of six research subagents times out. The final report covers five areas and reads as if it were complete. Reviewers only notice the missing area weeks later. Which change addresses this most directly?
  1. Fail the whole run whenever any subagent times out, so nothing is partial
  2. Have synthesis annotate coverage, naming which areas have gaps and why
  3. Increase the timeout of every subagent so that timeouts become very rare
  4. Ask the synthesis subagent to sound less certain throughout the report
Task 5.3: structure synthesis output with coverage annotations that show which findings are well supported and which areas have gaps because sources were unavailable. A throws away five good results. C makes the problem rarer but leaves it invisible when it happens. D hedges everything instead of identifying the gap.
Which two pieces of information in a subagent's error report most help the coordinator choose a recovery strategy? (Select 2)
  1. The failure type and the exact query that was attempted
  2. A full stack trace from the search client that threw
  3. Any partial results and possible alternative approaches
  4. A generic status message such as "search unavailable"
  5. The subagent's self-rated confidence that it would work
The guide's structured error context is failure type, attempted query, partial results and alternatives. B is noise for a coordinating model, D is the generic-status anti-pattern, and E is a self-reported confidence score, which the guide treats as unreliable.
Two credible surveys report 31% and 25% for "producers using AI". The synthesis agent writes "about 28% of producers use AI", citing both. What should it have done?
  1. Report the more recent survey's value and drop the older one
  2. Report the value from the survey with the larger sample size
  3. Report both values, each attributed, and mark the point as contested
  4. Leave out the statistic entirely, since the two sources disagree
Conflicting statistics from credible sources should be annotated with their attribution, not resolved arbitrarily. Averaging creates a number no source reported, and it hides that the surveys measured different things. A and B pick one value arbitrarily, and D throws away evidence.
A report flags a "contradiction": one source says 12% of studios use generative tools, and another says 40%. Investigation shows the first figure was collected in 2023 and the second in 2026. What prevents this error?
  1. Telling synthesis to always prefer the larger of two values it finds
  2. Requiring publication or collection dates in subagents' structured output
  3. Restricting the research to sources published within the last 30 days
  4. Adding a verify_fact call for every statistic before the synthesis runs
Task 5.6: require publication or collection dates so that temporal differences aren't read as contradictions. With dates, 12% → 40% is a trend. A is arbitrary, C throws away valid history, and D checks the values but not when they applied.
Between the search and synthesis stages, a summarizer condenses each subagent's output into a paragraph. Final reports make accurate claims, but reviewers can't trace which source supports which claim. What is the fix?
  1. Ask the final report to add a bibliography of every source consulted
  2. Give the synthesis agent web search so it can re-find each claim's source
  3. Drop the summarizer and give synthesis every raw page that was retrieved
  4. Pass structured claim–source mappings that each later stage must preserve
Attribution is lost at summarization steps unless the claim-to-source mapping is kept as structure and merged through each stage. A lists sources without linking them to claims. B re-researches in the wrong agent (2.3). C solves attribution by flooding the context (5.1).
The synthesis agent receives twelve subagent reports concatenated in arrival order. Its output reliably uses the first two and last two reports, and often misses findings from the middle ones. What is the best change?
  1. Shuffle the report order on each run so every report is used sometimes
  2. Split synthesis into twelve calls and concatenate their twelve outputs
  3. Put a key-findings summary first and use explicit headers per section
  4. Switch the synthesis agent to a model with a larger context window
This is the "lost in the middle" effect. The guide's mitigation is to put key findings at the beginning of aggregated input and organise the details with explicit section headers. A spreads the omissions around, B loses cross-report synthesis, and D doesn't change how the model attends to position.
Each research subagent returns about 8,000 tokens: its reasoning, every query it tried, and full page excerpts. With six subagents, the synthesis agent's context is mostly process, not findings. What should change?
  1. Have subagents return structured key facts, citations and relevance
  2. Have synthesis skim each report and skip what looks like reasoning
  3. Run synthesis twice and merge the two drafts into one final report
  4. Cap each subagent at fewer search queries so their reports are shorter
Task 5.1: when downstream agents have limited context budgets, change the upstream agents to return structured data (key facts, citations, relevance scores) instead of verbose content and reasoning chains. B still pays the token cost and relies on the model to filter. C doubles the cost. D makes the research worse in order to make it shorter.

  3. Move the subagent definitions into the coordinator's system prompt
  4. Give each subagent the Read and Grep tools that the coordinator has

  1. Ask the synthesis agent to expand the healthcare section from memory
  2. Return the draft and suggest the user ask about healthcare separately

Your document-analysis subagent also has the web search tool. It often searches the web for news that the search subagent has already covered, so the two duplicate work. What change fits best?

A customer gives the name "Maria Santos". get_customer returns three accounts with that name in the same city. What should the agent do next?

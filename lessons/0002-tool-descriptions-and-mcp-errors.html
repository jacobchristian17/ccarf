Tool descriptions and structured MCP errors

1 · The description is the selection mechanism

Claude picks tools by reading their names, descriptions and schemas, which the API places in the system prompt.Define tools → Tool use system prompt, Anthropic Docs. The guide calls descriptions "the primary mechanism LLMs use for tool selection", and the docs call them "by far the most important factor in tool performance". The docs ask for at least 3–4 sentences per tool, covering:Best practices for tool definitions. Compare the good and poor get_stock_price examples there.

  • What it does, and what it returns
  • When to use it, and when not to, naming the similar tool to use instead
  • Input formats, with examples ('12345', with or without a #)
  • Edge cases and limits, such as what it doesn't return or what an empty result means

Write it the way you'd brief a new hire: make the implicit context explicit.Writing effective tools for agents, Anthropic Engineering: "small refinements to tool descriptions can yield dramatic improvements".

Four repairs the guide names

SymptomRepair (2.1 skill)
Minimal descriptions ("Retrieves order details") and similar inputs, so the agent picks the wrong oneExpand the descriptions: inputs, example queries, edge cases, and the boundary with the sibling tool. This is the proportionate first step (sample Q2).
Two tools with near-identical descriptions (analyze_content vs analyze_document)Rename and re-describe to remove the overlap: analyze_content → extract_web_results, with a web-specific description.
One generic tool doing several jobs (analyze_document)Split it into purpose-specific tools with defined input/output contracts: extract_data_points, summarize_content, verify_claim_against_source.
Good descriptions, but the agent still misroutes on certain wordsReview the system prompt for keyword-sensitive instructions ("whenever the user says order…") that override the descriptions.
Split vs consolidate: not a contradiction

Exam (2.1)

Split a generic tool whose jobs need different contracts (extract vs summarise vs verify). The problem was one tool with unclear purpose.

Docs / eng blog

Consolidate thin API wrappers (list_users + list_events + create_event → schedule_event). The problem was many tools that serve one workflow.
The common rule: one tool per clear purpose. In sample Q2, consolidating into lookup_entity is described as "valid" but more effort than a first step warrants.

2 · MCP has two error channels

The MCP spec separates failures by who can fix them:MCP spec → Tools → Error Handling (2026-07-28). "Clients SHOULD provide tool execution errors to language models to enable self-correction."

ChannelExamplesWire format
Protocol errorUnknown tool, a malformed request, a server crashJSON-RPC error (e.g. -32602). The model is unlikely to fix it.
Tool execution errorAPI failure, invalid input, a business rule violationA normal result with isError: true and content the model can act on.

Everything in 2.2 lives in the second channel. The MCP isError flag becomes the API's is_error on the tool_result you built in Lesson 1.

3 · The error contract

A bare "Operation failed" leaves the agent guessing. Should it retry? Ask the customer? Apologise? Escalate? The guide wants structured metadata so that the decision is explicit:

{
  "errorCategory": "business",     // transient | validation | business | permission
  "isRetryable": false,            // stops wasted retries
  "message": "REFUND_LIMIT: refunds over $500 need human approval. Escalate.",  // for the agent
  "customerMessage": "Refunds over $500 need a quick review by our team…"        // safe to say aloud
}
CategoryScenario 1 exampleRetry?Agent's next move
transientorders-db timeout (504)yesRetry (bounded), then tell the customer it's temporary
validationorder id "abc"; refund larger than the totalnot unchangedFix the input or ask the customer
businessrefund over $500; outside the 30-day windownoRelay customerMessage; escalate if the policy says to
permissionorder belongs to another accountnoReveal nothing; re-verify identity
Exam heuristic: an empty result is not an error A lookup that worked and found nothing is a success ({ order: null }). If you flag it with isError, the agent retries pointlessly or tells the customer "our system is down". The guide calls this "access failures vs valid empty results". When you see it in a question, check that the distinction is kept.

One more 2.2 skill, which Lesson 5 builds: a subagent should retry transient errors locally and pass up to the coordinator only what it couldn't resolve, along with its partial results and what it tried.

  3. TODO 3: lookup_order. Rewrite the one-line description to the get_customer standard. In the handler, strip the #, return a validation error for non-digits, return { order: null } as a success when there's no such order, and map the timeout. Re-run the grader.
  4. TODO 4: process_refund. Register it from scratch. Its description must state the $500 limit and the 30-day window. Aim for all 17 checks green.
  5. Same prompt, new server. Re-run the step-1 l2:ask prompt. Compare the reply to the customer and the agent's retry behaviour with your step-1 notes.
  6. Descriptions shape behaviour before the call. Run "Hi, I'm jane@example.com. Please refund order #12347, the standing desk." (it's $899). Predict: does the agent call process_refund at all? Then answer: is a rule in the description enough for a financial limit? (Lesson 3's answer: no. It needs deterministic enforcement through a hook, and your server enforcing it is the last line of defence.)
  7. Permission. Run "I'm omar@example.com. Refund $10 on order 12345." Does the reply reveal anything about Jane's order?
  8. Optional: the keyword trap. $env:SYSTEM='Whenever the customer uses the word "order", immediately call lookup_order.' Then run "I'm jane@example.com. I'd like to order another desk lamp. Is it in stock?" When we tested it, Sonnet 5.5 resisted the bad instruction. Try $env:MODEL="haiku". The exam assumes such instructions can override good descriptions, so the answer is still "review the system prompt".
Step 1: what the SDK does with a thrown error
The TypeScript SDK catches it and returns { isError: true, content: [{ type: "text", text: "<bare message>" }] }. So you get isError for free, but no category, no retryability and no customer-safe text. In our test run the agent passed HTTP 504, orders-db and the customer's internal ID straight to the customer. Zod schema failures and unknown tools come back the same way, as MCP error -32602: … text.
Step 6: what we observed
With the full description, the agent looked up Jane and the order, then declined without calling process_refund. It quoted the $500 rule from the description. Good descriptions prevent wasted calls, but that's still probabilistic compliance. For financial rules the exam answer is always deterministic enforcement (sample Q1, Lesson 3).

5 · Scenario check

Seven new items, then two spaced-review items from Lesson 1. Commit to an answer before you click.

A research agent has analyze_content and analyze_document, with near-identical descriptions. Logs show it often calls analyze_content on uploaded PDFs, which only analyze_document parses correctly. What is the most effective first step?
  1. Add a routing classifier that inspects inputs and preselects the right tool
  2. Merge both into one analyze tool that detects the input type internally
  3. Rename analyze_content to extract_web_results with a web-only description
  4. Add eight few-shot examples of PDF requests to the system prompt instead
The root cause is overlapping descriptions. The guide's named skill is renaming and re-describing to remove functional overlap. A is over-engineered and bypasses the model's understanding. B is a bigger architectural change than a first step warrants. D adds tokens without fixing the overlapping definitions.
A single analyze_document tool is used for extracting figures, summarising, and checking whether a claim is supported. Outputs vary unpredictably and downstream code keeps breaking. What redesign does the guide recommend?
  1. Add a mode parameter and document every mode in a longer description
  2. Split it into purpose-specific tools, each with its own input/output contract
  3. Keep the one tool and validate its free-form output with a stricter parser
  4. Force the tool with tool_choice so it is called the same way every time
Splitting a generic tool into extract_data_points, summarize_content and verify_claim_against_source gives each job a defined contract, which fixes both selection and output shape. A keeps one ambiguous contract. C treats the symptom. D doesn't change what the tool returns.
Your tools have detailed, well-separated descriptions. Yet whenever a customer mentions their "account", the agent calls get_customer even when they gave an order number and asked about shipping. What should you check first?
  1. Whether get_customer's description is too long for the model to read fully
  2. Whether too many tools are configured on the agent for it to choose between
  3. Whether the system prompt has a keyword rule tying "account" to that tool
  4. Whether tool_choice is set to auto instead of forcing the lookup_order tool
When good descriptions still misroute on a particular word, the guide points to keyword-sensitive system prompt instructions that override them. With three tools, B isn't the issue. D would break every non-order turn.
On a refund that breaks the 30-day policy, process_refund returns isError: true with the text "Operation failed". The agent retries three times, then tells the customer the system is down. What fixes this at the source?
  1. Lower the retry limit in the system prompt from three attempts down to one
  2. Return errorCategory business, isRetryable false, and a customer message
  3. Throw an exception so the SDK reports the failure as a protocol-level error
  4. Return a success result with an empty body so the agent stops trying again
A uniform error hides the reason, so the agent guesses "transient". Structured metadata tells it not to retry and gives it something accurate to say. A treats the symptom. C makes things worse, because protocol errors are the channel the model is least able to use. D hides a real failure.
A search_orders tool returns isError: true, "not found" when a customer has no orders in the date range. The agent then retries and apologises for a "temporary outage". What is the correct change?
  1. Mark the not-found error as retryable false so the agent stops after one try
  2. Add a system prompt rule saying not-found errors are never outages to report
  3. Return a transient errorCategory so the agent can handle it with backoff retry
  4. Return a successful result with an empty list, since the query really worked
The query worked and found nothing. That's a valid empty result, not an access failure. Making it an error, however well labelled (A, C), still tells the agent something went wrong. B patches the prompt instead of fixing the tool's contract.
Which two fields does the guide name as structured error metadata that lets an agent make recovery decisions? (Select 2)
  1. errorCategory: transient, validation, business or permission
  2. stackTrace: the full server-side stack trace for later debugging
  3. isRetryable: a boolean saying whether a retry could succeed
  4. httpStatus: the raw upstream status code returned by the service
  5. dbHost: the internal database host that produced the failure
errorCategory and isRetryable, plus a human-readable description, are the guide's metadata. Stack traces, raw status codes and hostnames are the "opaque error codes or tracebacks" that the engineering blog says to avoid. In the lab they also leaked to the customer.
Your MCP flight tool receives a departure date in the past. How should the server report this so the model has the best chance to self-correct?
  1. As a JSON-RPC protocol error with code -32602 and an invalid-params message
  2. As a tool result with isError true and text explaining the valid date range
  3. As a successful result whose text quietly mentions that the date was ignored
  4. As a dropped connection, so the client times out and retries automatically
The MCP spec lists input validation errors as tool execution errors, reported with isError: true and actionable text. Protocol errors (A) are for unknown tools and malformed requests, and the spec says the model is less likely to recover from them. C hides the failure; D is worse.
A teammate's loop ends when the reply contains "Final answer:". After a prompt rewrite, Claude stops writing that phrase and every run hits the 25-turn cap. What is the correct fix?
  1. Add the phrase back into the system prompt as a required closing marker
  2. Raise the cap to 50 turns so that long tasks have room to finish properly
  3. End the loop when stop_reason is end_turn and keep the cap as a backstop
  4. End the loop at the first response that contains any text block at all
Parsing natural language is an anti-pattern, and so is a cap as the primary stop. stop_reason is the protocol signal. D is the third anti-pattern: text alongside tool_use doesn't mean done.
You want Claude to write a one-line explanation to the user and call lookup_order in the same turn. Which configuration does that?
  1. tool_choice any, with an instruction to explain the reasoning first
  2. tool_choice auto, with the user message asking it to use lookup_order
  3. tool_choice forced to lookup_order, with disable_parallel_tool_use
  4. tool_choice none for one turn, then forced to lookup_order the next
Under any or forced tool, the API prefills the turn, so no text comes before the tool_use. The docs' recommendation is auto plus an explicit request in the user message. D spends two turns and is still forced on the second.

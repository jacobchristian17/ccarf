Decomposition, sessions and long exploration

Long tasks fail in three places: how the work is split up, which context you carry forward, and what happens when the context runs out or the process dies. Each one has an exam-grade answer, and they all come down to deciding what the next agent starts from.

1 · Two ways to decompose (1.6)

Fixed sequential pipeline (prompt chaining)Dynamic adaptive decomposition
Use whenThe steps are known in advance: a predictable, multi-aspect reviewThe task is open-ended, and what comes next depends on what you find
ShapeStep 1 → step 2 → step 3, with code checks between steps if you want themMap, then pick high-impact areas, then a prioritised plan that changes as dependencies turn up
Guide's exampleReview each file on its own, then run a cross-file integration pass"Add comprehensive tests to a legacy codebase"

Anthropic's own framing is the same. Prompt chaining suits tasks that "can be easily and cleanly decomposed into fixed subtasks", and it trades latency for accuracy. Orchestrator-workers suits "complex tasks where you can't predict the subtasks needed".Building Effective AI Agents, "Workflow: Prompt chaining" and "Workflow: Orchestrator-workers". Task statement 1.6, md/CCAR-F/sections/07.

Why per-file plus integration? A single pass over many files suffers attention dilution: depth becomes uneven, obvious bugs get missed, and the same pattern gets flagged in one file and passed in another. The fix has two halves:

  • Per-file local passes, each seeing only its own file. They find local issues consistently.
  • One integration pass that receives the per-file findings, not the raw source again, and looks only for cross-file problems: data flow, and contracts one module assumes about another.

Keep Lesson 4 in mind: sample Q7's narrow decomposition (creative industries split into three visual-arts subtasks) is a 1.2 failure that shows up as a decomposition problem. When the subagents all succeed and the coverage is still wrong, look at what they were assigned.

2 · Sessions: resume, fork, or start fresh (1.7)

SituationMove
Prior context is mostly valid, and you're continuing yesterday's investigationResume the named session: claude --resume refund-analysis
…but a few files changed since thenResume, and say which files changed so it re-analyses only those, not the whole codebase
Most of what it read is now staleStart fresh with an injected structured summary. Resuming would bring back stale tool results that the model trusts
Two divergent approaches from one shared analysisfork_session: each branch keeps the baseline, and the original stays unchanged

The failure behind this table: a resumed session's earlier tool results are still in context and look just as authoritative as they did yesterday. The model has no idea the files moved under it. The SDK docs suggest the same alternative the guide does: "capture the results you need (analysis output, decisions, file diffs) as application state and pass them into a fresh session's prompt. This is often more robust than shipping transcript files around."Agent SDK → Work with sessions, "Resume across hosts" and "Fork to explore alternatives". Task statement 1.7.

What a fork does and doesn't share A fork copies the conversation history. It doesn't copy the filesystem. In the docs' words: "If a forked agent edits files, those changes are real and visible to any session working in the same directory." For branches that each edit code, give each one its own worktree, or use file checkpointing.

3 · Long exploration without losing the thread (5.4)

The symptom to recognise: late in a long session, answers turn inconsistent and refer to "typical patterns" instead of the specific classes found earlier. Anthropic calls the mechanism context rot: "as the number of tokens in the context window increases, the model's ability to accurately recall information from that context decreases."Effective context engineering for AI agents: context rot, compaction, structured note-taking, sub-agent architectures.

TechniqueWhat it does
Scratchpad fileThe agent records key findings outside the context window and reads them back for later questions. Anthropic's term is "structured note-taking", for example "maintaining a NOTES.md file"
Subagent delegationVerbose discovery ("find all test files", "trace refund flow dependencies") runs in a clean context. The main agent gets back a summary and keeps the high-level view
Phase summariesSummarise phase N's key findings and inject them into the initial context of the subagents for phase N+1
Manifest for crash recoveryEach agent exports structured state to a known location. On resume, the coordinator loads a manifest and injects that state into the agents' prompts
/compactSummarises the conversation so far to free context while discovery output piles up. It takes optional focus instructions

Anthropic's long-running-harness post builds the same pattern: a progress file plus git history so each new context window "get[s] up to speed", and a JSON feature list because "the model is less likely to inappropriately change or overwrite JSON files compared to Markdown files". That's the argument for a structured manifest over free-text notes.Effective harnesses for long-running agents. /compact [instructions]: Commands.

Exam answer vs current reality

Exam (1.7, 5.4)

--resume <session-name> continues a named session. fork_session creates independent branches. /compact reduces context use. Manifests are your own design: agents export state, and the coordinator loads it on resume.

Today (CLI 2.1.289, SDK v0.3.289)

Name a session with -n / /rename. In the SDK, title sets the name, and we checked that claude -r refund-analysis found an SDK session by that title. Forking is --fork-session on the CLI, forkSession: true with resume in TS (Python: fork_session=True), or the standalone forkSession(id) function. Interactive mode adds /branch (switch into a copy) and /fork (a background copy).
The concepts are the same on both sides. If an option says fork_session, read it as "fork from a shared baseline".CLI reference: --resume "by ID or name", --name, --fork-session. SDK types: sdk.d.ts Options.forkSession, Options.title, forkSession().

  5. TODO 3: reviewChain + EXPLORER_PROMPT (decompose.ts). Get l6:check to 57/57.

5 · What we observed (2026-10-05, Haiku 4.5 agents, SDK v0.3.289)

Prediction check: stale resume (small change, no notice)
0 files re-read. In 8.9 s the resumed session answered confidently with the old code: "postCredit … Is it safe to call twice? NO". Both parts were wrong, because the code now has an idempotent postRefundCredit. The earlier tool results were still in context, and nothing suggested they were stale. After change big with FORCE=resume it happened again: 0 re-reads, old function names, and no mention of the event-driven rewrite.
(A note on method: our first draft of the follow-up question said "as the code is NOW", and with that wording the model did re-read. A real user doesn't word questions that way, so the lab now asks neutrally. The notice has to carry that information.)
Reference planSession: resume with notice (small) · fresh with summary (big)
Small: RESUME with a notice naming 2 files. It re-read exactly those 2 and answered correctly (postRefundCredit, idempotent, with the key format), and it flagged that two refunds of the same amount would collide on the key. 12.4 s.
Big: 7 of 9 files stale → FRESH. The injected summary was 5,238 chars, with 17 of 19 findings tagged [STALE … re-verify]. The new session found refund-worker.ts:14, a file the old session had never seen, and answered correctly.
Prediction check: fork
Both forks (unit tests with mocks, and integration tests on the real ledger) re-read 0 files and built on the shared analysis. They got distinct session ids. When the original was resumed afterwards it kept its id and replied "We haven't chosen one yet". Neither fork had touched it. 55 s in total.
Explore with CRASH_AFTER=2: starter vs reference
Starter: no manifest, so the rerun started from scratch and ran all four agents again (165 s, 38 file reads, no injected context). Every agent re-explored the same 9 files.
Reference: the refund-tracer got 3,321 chars of mapper state. The rerun skipped 2 agents, test-finder got 6,773 chars, and the planner got 9,356 chars and read only 2 files, yet named 6 of 6 specific functions. 105 s, 12 reads.
Two things that weren't ideal. (1) The planner cited SCRATCHPAD.md:73 instead of refund-service.ts. That passed the "cite files you read" rule, because it had read the scratchpad, but provenance is now one hop from the code. That's the Lesson 5 problem again, with a notes file as the summarization step. (2) The scratchpad reached 92 finding lines in one run. Append-only notes need curation, or they become the next source of context rot.
Review chain: single pass vs per-file + integration
Single pass (starter, 26 s): it caught the non-idempotent credit and missed settlement's dependency on the ledger entry shape. Chain (reference, 9 steps, 48 s): it caught both, and found local issues in the per-file passes. Caveat: the fixture has 8 small files, so dilution is mild here. The guide's scenario is a 14-file PR, and the gap grows with size. The integration pass also cited line numbers it never saw (it only gets findings), so an integration pass can only be as good as the per-file findings it receives.

6 · Scenario check

Ten new items, then six spaced-review items: three from Lesson 5 and three from Lesson 4. Commit to an answer before you click.

A review agent gets a 14-file pull request in one prompt. Its comments are detailed on some files and shallow on others. It misses an obvious null dereference, and it flags a pattern in one file while approving the same pattern in another. What is the best restructuring?
  1. Switch to a model with a larger context window for the reviews
  2. Review each file in its own pass, then run one cross-file pass
  3. Run the same full review three times and keep the majority view
  4. Add an instruction to review every file with equal, careful depth
This is attention dilution. Per-file local passes give consistent depth, and a separate integration pass catches cross-file issues. A doesn't change how attention spreads across the input. C triples the cost and keeps the dilution. D asks for the behaviour without changing the structure that causes the problem.
You're asked to "add comprehensive tests to a legacy codebase" of about 400 files with almost no tests. Which decomposition fits best?
  1. A fixed chain that writes tests for every file in alphabetical order
  2. One subagent per file, all spawned in parallel straight away
  3. Map the structure, find high-impact areas, then plan and adapt
  4. Write tests first for whichever files changed most recently in git
Open-ended tasks call for dynamic decomposition. Map the structure, identify high-impact areas, and create a prioritised plan that adapts as dependencies are discovered. A and B are fixed plans for a task whose subtasks you can't predict, and B also floods the coordinator with 400 results. D uses a proxy for importance that may not track risk.
Every week, each new vendor contract has to be checked against the same six clauses: liability, termination, data handling, payment terms, IP and jurisdiction. Which pattern fits best?
  1. A fixed sequential pipeline with one step for each clause check
  2. A dynamic plan that the agent works out from each contract's text
  3. A coordinator that decides at run time which clauses are relevant
  4. A single open-ended prompt asking the agent to review the contract
The steps are known in advance and the same every time, so prompt chaining fits: predictable, multi-aspect, and easy to check between steps. B and C add adaptivity the task doesn't need, which means more variance and more cost. D loses the structure that makes the review consistent.
Your review chain has per-file passes followed by an integration pass. The integration prompt contains every file's full source and all the per-file findings, and its output is as shallow as the old single-pass review. What change helps most?
  1. Add a second integration pass that reviews the first one's output
  2. Give it the per-file findings, not the source, and a cross-file focus
  3. Remove the per-file passes, since the integration pass sees it all
  4. Run the integration pass first, so per-file passes can build on it
Putting the full source back into the integration prompt recreates the dilution you split the review to avoid. The integration pass should work from the structured per-file findings and look only for cross-file problems (data flow, contracts). A adds cost without fixing the input. C goes back to a single pass. D reverses the dependency.
Yesterday you spent two hours in a session named billing-audit analysing a billing module. Overnight, a teammate changed 2 of the 30 files that session read. What is the best way to continue?
  1. Start a new session and have it explore the billing module again
  2. Resume billing-audit and continue, since most files are unchanged
  3. Resume billing-audit and say which 2 files changed, for a re-read
  4. Resume billing-audit and ask it to re-read all 30 files first
The prior context is mostly valid, so resume the session, and tell it about the specific changes so it re-analyses only those files. A throws away two hours of valid work. B leaves stale tool results that the model will trust: in our lab it re-read nothing and confidently described the old code. D re-explores everything when only 2 files need it.
After a large refactor that changed most of the files an earlier session analysed, you resume it. Its answers now refer to functions that no longer exist. What should you have done?
  1. Resume it anyway and correct each stale answer as it comes up
  2. Fork the old session so that the stale analysis stays intact
  3. Run /compact on the old session before asking any new question
  4. Start fresh, injecting a structured summary of the prior findings
When prior tool results are mostly stale, a new session with an injected structured summary is more reliable than resuming. The summary carries the conclusions, with the stale ones flagged for re-verification. A puts the job on you. B copies the stale context into a new branch. C compresses the stale results but they're still there, and still stale.
A session has finished a detailed analysis of a legacy module. You want to compare two refactoring approaches, strangler-fig and a full rewrite, each building on that same analysis without affecting the other. What fits best?
  1. Fork the analysed session twice, one branch per refactoring approach
  2. Resume the analysed session and explore both approaches in sequence
  3. Start two new sessions and have each redo the module analysis first
  4. Ask the analysed session to compare both approaches in one answer
fork_session creates independent branches from a shared baseline. Each keeps the analysis, and neither affects the other or the original. B contaminates the second approach with the first. C repeats the analysis. D gives neither approach a full exploration. In our lab, both forks re-read 0 files.
Three hours into exploring a large codebase, the agent's answers drift. It describes "a typical repository pattern" instead of the LedgerGateway class it traced an hour ago, and it contradicts an earlier finding. What is the most effective change?
  1. Repeat the original task instructions at the start of every prompt
  2. Have the agent record findings in a scratchpad and consult it later
  3. Switch to a model with a larger context window and keep on going
  4. Restart the exploration from scratch whenever answers start drifting
This is context degradation. A scratchpad file keeps key findings outside the context window, and the agent references it for later questions. A re-sends instructions but not findings. C delays context rot rather than preventing it. D throws away the work, and the degradation returns.
A six-agent codebase-analysis pipeline crashes after the third agent finishes. On restart, the coordinator runs all six from scratch, and the later agents never see what the first three found. What fixes both problems?
  1. Retry each agent automatically until the whole pipeline finally succeeds
  2. Run all six agents in parallel so a crash interrupts less of the work
  3. Agents export state to a known location; the coordinator loads a manifest
  4. Keep the coordinator's full conversation and resume that session instead
Structured state persistence: each agent exports its state, and the coordinator loads a manifest on resume and injects it into the remaining agents' prompts. That handles both recovery and handoff. A doesn't fix either problem. B breaks the phase dependencies. D depends on one transcript surviving, and it doesn't give the subagents the earlier findings.
Exploring a monorepo, the main agent's context fills with long Grep and Glob output from discovery work, and its coordination gets worse. Which two actions address this? (Select 2)
  1. Delegate discovery questions to subagents that return summaries
  2. Restate the overall goal more forcefully in the system prompt
  3. Use /compact to summarise the verbose discovery output so far
  4. Raise max_tokens so the agent can write longer final answers
  5. Disable the Grep tool so that discovery uses only Read calls
Subagents keep verbose exploration in their own clean contexts and return condensed summaries. /compact frees context that discovery output has filled. B doesn't remove any tokens. D affects output length, not context. E makes discovery slower and noisier.
A patent-search subagent hits a rate limit on two of its five queries. It decides on its own to drop those two subtopics and returns status: "complete" with three findings. The final report never mentions them. What should it have done?
  1. Abort the research run so a human can deal with the rate limit
  2. Keep retrying the two failed queries until they eventually succeed
  3. Return partial results and the structured error to the coordinator
  4. Swap in two other subtopics that it was able to search successfully
The subagent made a recovery decision that belongs to the coordinator, and it hid the failure as success. It should report partial with failure type, attempted queries and alternatives, so the coordinator can re-delegate or annotate the gap. A terminates the run, B can hang, and D changes the scope without telling anyone. Lesson 5, reference.
The synthesis agent's brief cites a source for every claim. The coordinator then writes the final answer for the user, and the citations become "(industry sources)". Where is the fix?
  1. In the searchers, which should return more detailed source metadata
  2. In the final hop, which must keep the claim–source mapping it receives
  3. In synthesis, which should send fewer claims so each can be cited
  4. In the user-facing UI, which should show a full bibliography at the end
Attribution is lost at summarization steps, and the coordinator's rewrite is one. The mappings reached it intact, so the fix belongs at that hop (a prompt rule, or a check on the final text). A and C fix stages that worked. D lists sources without linking them to claims. Lesson 5.
A support agent calls lookup_order several times per conversation. Each call returns about 45 fields, including warehouse codes and carrier internals, and the task needs about 5. Long conversations start losing track of what the customer asked. What is the best first change?
  1. Summarise the whole conversation after every third order lookup
  2. Move to a model with a larger context window for the long chats
  3. Ask the agent to ignore any fields it judges to be irrelevant
  4. Trim each tool result to the relevant fields before it builds up
Task 5.1: trim verbose tool output to the fields the task needs before it accumulates in context. A loses detail through repeated summarisation. B delays the problem. C still pays for every token and relies on the model to filter. Lesson 5, reference.
A coordinator spends ten turns finding which three contracts are relevant. It then spawns an analysis subagent with the prompt "Analyse the relevant contracts for risk". The subagent analyses the wrong contracts. What is the cause?
  1. The subagent's model is too small to work out which contracts matter
  2. Subagents don't inherit the coordinator's history; pass the context
  3. The subagent's tool set is missing a contract search capability
  4. The coordinator should have run the analysis itself instead of delegating
A subagent receives only its definition and the prompt it is given. It doesn't see the coordinator's conversation. The prompt must say which contracts and why. A and C fix the subagent, D gives up on delegation. Lesson 4, reference.
Asked about "AI in healthcare", a coordinator spawns subagents for diagnostic imaging, radiology workflows and pathology slides. Each returns excellent work, but the final report has nothing on drug discovery, administration or patient-facing tools. What is the root cause?
  1. The searchers' queries were too narrow within each assigned area
  2. The synthesis agent dropped the sections it considered less relevant
  3. The coordinator's decomposition only covered image-based diagnosis
  4. The healthcare corpus lacks sources on the missing application areas
The subagents did what they were assigned, and the assignments covered only one slice of the topic. This is the sample Q7 pattern. A, B and D blame agents or data that were working correctly. Lesson 4.
A ticket-drafting subagent often needs a customer's plan tier, and goes back through the coordinator each time. Logs show that 90% of these are simple lookups and 10% need a full account investigation. What is the best change?
  1. Give the drafting agent every account tool so it never has to return
  2. Give it a scoped plan-tier lookup tool; route the rest via the coordinator
  3. Have the coordinator preload every account field into each draft prompt
  4. Batch all lookups and return them to the coordinator at the end of drafting
Least privilege for the common case: a scoped tool covers the frequent simple need, and complex cases keep the existing coordination path. A over-provisions, C floods the context with guessed data, and D blocks the drafts that depend on the answers. Lesson 4.

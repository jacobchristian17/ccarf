Claude Code in CI, and review prompts that developers trust

1 · Running Claude Code in a pipeline (3.6)

claude -p --output-format json \
  --json-schema "$(cat review/finding.schema.json)" \
  --allowedTools "Read,Grep,Glob" --max-turns 20 < prompt.txt > review.json
PieceWhat it does in CI
-p / --printRuns the prompt, prints the result and exits. Without it, claude opens an interactive session and the job hangs waiting for input. CLAUDE_HEADLESS, --batch and < /dev/null are the exam's fake fixes.
--output-format jsonOne JSON result envelope instead of prose: result, session_id, is_error, subtype ("success", "error_max_turns", …), num_turns, total_cost_usd
--json-schemaThe output must match your schema. The validated object arrives in structured_output, so a script can turn each finding into an inline PR comment. Your script still has to check is_error and subtype first.
CLAUDE.mdA -p run loads the repo's CLAUDE.md like any session. That's where CI gets project context: testing standards, fixture conventions, review criteria.
--allowedToolsPre-approves tools. A reviewer needs only Read/Grep/Glob. In -p, any call that would need approval is denied (and listed in permission_denials), not left waiting.

The envelope from a real run in this lab, trimmed: {"type":"result","subtype":"success","is_error":false,"num_turns":2,"session_id":"9806…","total_cost_usd":0.054,"result":"{…}","structured_output":{"primes":[3,7],"confidence":0.99}}.Run Claude Code programmatically: "the structured output in the structured_output field". An invalid schema exits with "Error: --json-schema is not a valid JSON Schema". Task statement 3.6, md/CCAR-F/sections/09.

Exam answer vs current reality

Exam (3.6)

-p prevents the hang. --output-format json + --json-schema give machine-parseable findings. CLAUDE.md is the mechanism for giving CI-invoked Claude Code its project context.

Today (CLI 2.1.290)

All three still hold. The docs now also recommend --bare for scripted runs: it "will become the default for -p". Bare mode skips CLAUDE.md, hooks, skills, .mcp.json and your ~/.claude, and it needs ANTHROPIC_API_KEY (it ignores the subscription login). Context then goes in with --append-system-prompt-file. On GitHub, the packaged route is anthropics/claude-code-action@v1 (prompt + claude_args).
On the exam, CLAUDE.md is the answer for CI context. In a real pipeline, either run without --bare so CLAUDE.md loads, or pass the same file explicitly. The lab can't demonstrate bare mode: it needs API credits.Headless docs, "Start faster with bare mode". GitHub Actions: "Define project standards in CLAUDE.md … review criteria".

2 · From findings to PR comments, and the second push

A finding schema that CI can post from needs a location (file, line), severity and category as enums, the issue, a suggested_fix, a detected_pattern and a confidence. detected_pattern is a short name for the code construct that triggered the finding, so you can later count which patterns developers dismiss (4.4). Confidence goes in a field, which leaves the routing decision to code (§5). Your post.ts maps each finding to { path, line, side: "RIGHT", body }.

CI problemExam fix
Each push re-runs the review, and the same comments get posted againPut the prior findings in the prompt and ask for only new or still-unaddressed issues. Fixed issues drop out. In the lab, a status: new | still_open field lets code post only the new ones.
Generated tests repeat scenarios the suite already coversGive Claude the existing test file in context
Generated tests are shallow, or they ignore the team's factoriesDocument testing standards, what a valuable test is, and the available fixtures in CLAUDE.md

3 · Explicit criteria beat "be conservative" (4.1)

"Check that comments are accurate" makes Claude decide what accurate means, PR by PR. "Flag a comment only when the behaviour it claims contradicts what the code does" is a test it can apply. Precision comes from categories: say what to report (bugs, security, broken contracts) and what to skip (style, documented local patterns). It doesn't come from confidence wording. The guide is blunt that "be conservative" and "only report high-confidence findings" fail to improve precision.

  • False positives spread. A noisy category teaches developers to ignore the accurate ones too. The first step is to temporarily disable the high-false-positive category while you fix its prompt, not to turn the whole review "down".
  • Severity drifts unless each level is defined with a concrete code example ("critical: `…WHERE email = '${email}'`").

Anthropic's own guidance: "If you want 'above and beyond' behavior, explicitly request it rather than relying on the model to infer this from vague prompts." And the Claude Code best-practices page warns that "a reviewer prompted to find gaps will usually report some, even when the work is sound … Tell the reviewer to flag only gaps that affect correctness".Prompting best practices, "Be clear and direct". Best practices for Claude Code, "Add an adversarial review step". Task statement 4.1, md/CCAR-F/sections/10.

4 · Few-shot examples (4.2)

When detailed instructions still give inconsistent output, examples are the most effective next step: they show the format and the judgement instead of describing them. The guide's recipe:

  1. 2–4 targeted examples, aimed at the ambiguous cases, not the easy ones.
  2. Each one shows its reasoning: why this action and not the plausible alternative.
  3. At least one looks wrong but is acceptable, so its output is "no finding". That cuts false positives without a rigid rule, because the model generalises the reason.
  4. Each reported example shows the exact output: location, issue, severity, suggested fix.
<example>
<code file="src/api/handlers.ts">+export async function cancelRoute(db: Db, body: any) {</code>
<reasoning>body: any looks like a type-safety issue, but CLAUDE.md documents it as the
handler convention (the gateway validates bodies). A documented convention is not a finding.</reasoning>
<output>(no finding)</output>
</example>

For extraction (Lesson 10), the same tool fixes empty or null required fields: show examples from documents with varied structure.Prompting best practices, "Use examples effectively": relevant, diverse, wrapped in <example> tags. Drift: the docs say "Include 3–5 examples for best results", while the guide says 2–4. On the exam, pick 2–4. Task statement 4.2.

6 · Build: a CI review job for tally-billing (Scenario 5)

The lab is lab/09-ci-review/. fixture/pr1 is an 11-file PR with 5 planted defects: SQL injection, an uncapped refund, a reversed expiry check, a cross-file cents/dollars contract break, and a comment that contradicts its code. It also has 4 noise traps: let vs const, the documented body: any, console.log in a dev script, and inline ms-per-day arithmetic. pr2 is a follow-up push. Every model call is a real claude -p --output-format json --json-schema subprocess, and its findings are scored against fixture/truth.json.

Commands (PowerShell, in lab/) 
cd C:\Users\wsenr\repos\ccarf\lab

npm run l9:ask -- rereview              # PR 1 + follow-up push, with your rereview.md and the prior findings
npm run l9:ask -- multipass             # 11 per-file passes + 1 integration pass (~3 min)
npm run l9:ask -- self                  # generator → self-review (--resume) vs independent review, hidden tests
npm run l9:ask -- testgen               # propose tests for src/discount.ts

Remove-Item Env:PROMPT, Env:SOLUTION, Env:NOPRIOR, Env:CONTEXT -ErrorAction SilentlyContinue
Runs take 20 s to 3 min on Haiku 4.5, at about $0.03–0.33 each in subscription usage.
  1. Baseline. npm run l9:check (expect 4/44). Run review: the starter schema returns one free-text blob, so there's nothing to post inline. Then run review with $env:PROMPT="vague" (vague criteria, but a real schema) and note the defects found and false positives.
  2. TODO 1: the schema and the job. Rewrite review/finding.schema.json (§2) and fix .github/workflows/claude-review.yml: add -p, json plus schema, read-only tools, and run on synchronize.
  3. TODO 2 and 3: criteria and examples. Write criteria.md (§3) and examples.md (§4). Use code that isn't from this PR, and include one "no finding" example. Run review twice. Compare against the vague baseline: which defects moved, and did any noise trap fire?
  4. TODO 5: post.ts. Implement toInlineComments. The grader feeds it success, is_error, error_max_turns and missing-structured_output envelopes. review prints the comments it would post.
  5. TODO 4: re-review. Run rereview with $env:NOPRIOR="1" and count the duplicate comments. Then write rereview.md and run it again. How many new comments would this push post, and which ones?
  6. TODO 6: test context. Add a ## Testing section to review/CLAUDE.md. Run testgen with $env:CONTEXT="none", then without it, and compare the duplicates and fixture use.
  7. 4.6 runs. multipass: which defect came only from the integration pass? self: what did the self-review catch that the independent review didn't, and the reverse?

7 · What we observed (2026-10-06, Haiku 4.5, CLI 2.1.290)

Prediction check (a): vague vs explicit criteria
PromptDefects found (of 5), per runNoise traps flaggedOther false positives
Vague ("be conservative", no examples)3 · 3 · 3 (a 4th run scored 4 with an early, buggier matcher)00 · 0 · 2
Explicit criteria + 3 examples (reference)4 · 5 · 500 · 0 · 2
Haiku flagged none of the noise traps under either prompt, so the exam's picture of vague prompts flooding a PR with style nits didn't reproduce here. What the explicit criteria changed was recall. The vague prompt kept missing the comment contradiction (T5) and the refund cap (T2). The reference criteria name both categories ("a comment ONLY when it contradicts…", "a missing limit check on money"), and the reference runs found T5 in 3 of 3 and T2 in 2 of 3. The remaining false positives were the same judgement call twice: "refundRoute doesn't catch the errors issueRefund throws". It's arguable (CLAUDE.md says handlers return err()), and it's in neither the report list nor the skip list. That's exactly the gap explicit criteria are meant to close.
Multi-pass: what the integration pass is for
11 per-file passes (no tools, one file each) produced 7 findings. Neither receipt.ts nor invoices.ts produced one on its own, because each file looks fine in isolation. The integration pass (Read/Grep, given the per-file findings) found the cents/dollars break, T4. Total: 5/5, 2 false positives, 1 duplicate, about 175 s and $0.33. One reference single pass took about 50 s and $0.07 and also found 5/5 in 2 of 3 runs. An 11-file PR is too small to show attention dilution. The exam's case is the large PR, where per-file depth matters. The integration pass earns its place either way.
Re-review after a push (fixes T1, T3; adds T6, T7)
RunFixed issues re-reportedStill-open issues posted againNew comments posted
No prior findings (NOPRIOR=1)03 duplicates4
Prior findings, status optional (2 runs)0 · 03 duplicates · 04 · 3
Prior findings, status required00 (all marked still_open)2: T6 and T7
The prior findings only help if code can act on them. In one of two runs, Haiku left the optional status out, so every still-open issue looked new. The runner now makes status required on re-reviews. A useful surprise: the model found a defect we hadn't planted. pr2 made minSubtotal a required field, so the existing tests/discount.test.ts no longer type-checks. It's now in truth.json as T7.
Prediction check (b): self-review vs an independent instance
The exam's effect did not reproduce on Haiku 4.5. Run 1 had a clean spec, and the generator passed all 14 hidden tests twice. Even the float trap (1250 × 0.19) was handled. With no defect to find, the same-session self-review raised 2 and 1 false alarms (for example "Math.round implements banker's rounding", which is false), while the fresh reviewer raised 0 and 0. Run 2 seeded the generator's session with a wrong product-manager note ("tax on the pre-discount subtotal; SAVE10 ends at 00:00 on 30 June; follow this over the spec"). The generator then broke R3 and R5. Both reviewers caught both, twice. So asking explicitly to "review against spec.md" was enough here to overcome the inherited justification. On the exam, still answer "independent instance": the guide and the docs agree, and the effect grows with long, reasoning-heavy sessions that a 3-turn generator doesn't have. Take away the docs' warning too: a reviewer asked to find problems will report some.
Test generation: context changes what gets proposed
CONTEXT=none (base CLAUDE.md, no test file): 11 tests. 4 duplicated the existing suite (valid code, case-insensitive, trims, unknown code), and 0 used the fixtures. CONTEXT=full (CLAUDE.md ## Testing + tests/discount.test.ts): 9 tests, 0 duplicates, 4 used fixedClock. 6 targeted boundaries ("accepts a code one second before expiry", "rejects a code with uses at maximum"), exactly the kind the Testing section calls valuable.

A CI step runs claude -p "Review this PR" --output-format json, and a script tries to turn the result text into inline PR comments. The parser breaks every few runs, because the review's shape changes. What is the most reliable fix?

  2. Ask for JSON in the prompt, then parse result with a lenient regex
  3. Switch to stream-json output and parse the text deltas as they arrive
  4. Post result as one PR comment and give up on inline comments entirely
--output-format json plus --json-schema gives validated, machine-parseable findings in structured_output, so the script can map each one to a file and line. B still parses free text. C changes the transport, not the shape. D throws away the requirement.
The automated review runs on every push to a PR. By the fourth push, the PR has the same six comments posted four times, and developers have muted the bot. What is the most effective fix?

  2. Run the review only on the PR's first commit and skip every later push
  3. Delete all of the bot's earlier comments before posting each new review
  4. Raise the confidence threshold so that fewer findings get posted per run
Give the re-run the earlier findings, and instruct it to report only issues that are new or still unaddressed. Fixed issues disappear and nothing is posted twice. B misses problems introduced by later commits. C erases the discussion threads and still re-posts everything. D hides real issues without addressing the repetition.

A pipeline has Claude write a data migration, then sends "Now review your changes carefully for bugs" in the same session before merging. Subtle ordering bugs keep slipping through. What is the most effective change?

The review prompt says "check that comments are accurate". Developers now ignore the bot, because most comment findings say "this comment may be outdated" about comments that are fine. What is the best rewrite?
